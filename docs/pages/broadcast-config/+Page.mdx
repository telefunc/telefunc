**Environment**: server.

<TelefuncStreamBeta />

```ts
// Environment: server

import { config } from 'telefunc'

config.broadcast = {
  transport: undefined, // A BroadcastTransport that carries Broadcast across servers
}
```

`transport` is a `BroadcastTransport`:

```ts ts-only
type BroadcastTransport = {
  send(key: string, payload: string): { seq: number; timestamp: number } | Promise<{ seq: number; timestamp: number }>
  listen(key: string, onMessage: (payload: string, info: { seq: number; timestamp: number }) => void): () => void
  sendBinary(key: string, payload: Uint8Array): { seq: number; timestamp: number } | Promise<{ seq: number; timestamp: number }>
  listenBinary(key: string, onMessage: (payload: Uint8Array, info: { seq: number; timestamp: number }) => void): () => void
}
```

> Without a `transport`, Broadcast uses the installed backend (such as <Link href="/redis"><code>@telefunc/redis</code></Link>) or, with none installed, stays in memory and reaches only subscribers on the same server. A configured `transport` takes precedence over both. Assigning another one, for example on hot reload, moves live subscriptions to it, and their `info.seq` then comes from the new transport, which may number lower.

> `send()` and `sendBinary()` return the `{ seq, timestamp }` they assigned, and `onMessage` gets the same pair. Telefunc hands it to <Link href="/channel#broadcast">`Broadcast.subscribe()`</Link> subscribers as `info.seq` and `info.timestamp`, unchanged: it neither reorders nor drops a repeated or lower `seq`. Because `info.seq` is monotonic per key, a key's text and binary messages take their `seq` from one counter that every server shares; with a counter per server, two servers' messages on a key cross numbers.

> `seq` must be a positive safe integer and `timestamp` a non-negative safe integer such as `Date.now()`; otherwise the `publish()` fails, or `onMessage` throws.

> Telefunc calls `listen()` and `listenBinary()` once per key on a server while that key has subscribers there, and calls the function they return before it listens on the key again. It passes on every message `onMessage` gets, so a `listen()` that also delivers messages sent before it hands those to subscribers as new.

> A key's subscription is ready once `listen()` returns, so a publish on the same server right after a `subscribe()` goes out at once and must reach that listener. With a broker that subscribes asynchronously (a Kafka consumer joining its group, say), the transport delivers its own sends to its listeners on that server.

> A `send()` that throws or rejects makes the `publish()` fail, and no subscriber gets the message. Telefunc isn't told of a dropped connection and never calls `listen()` again on its own: the transport reconnects and keeps calling the `onMessage` it was given.

> A key is any well-formed string, such as `'room:lobby'`; a transport whose broker restricts names (NATS subjects) encodes it. Telefunc caps no payload: a page's publish is under 64 MiB (see <Link href="/channel#binary-data">Binary data</Link>), and a server's `Broadcast.publish()` has no limit.

> A transport that sends `sendBinary()`'s `payload` after `sendBinary()` returns (after an `await`, or from a queue) must send a copy: the publisher may reuse its buffer once <Link href="/channel#broadcast">`publishBinary()`</Link> returns.
