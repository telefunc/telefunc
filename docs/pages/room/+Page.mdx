`Room` adds multi-party **rooms** on top of <Link href="/channel">channels</Link>: presence (who's in the room), participant metadata, per-member streams, private messages, and admin controls.

> Use rooms for chat, video calls, game lobbies, collaborative editing — anything where *who is connected* matters. When you only need messaging or pub/sub, use <Link href="/channel">channels</Link> instead.

| | <Link href="/channel#new-channel">`new Channel()`</Link> | <Link href="/channel#new-broadcastchannel">`new BroadcastChannel()`</Link> | `Room` |
|---|---|---|---|
| Server-client pipe | ✓ | ✓ | ✓ |
| Topic-based pub/sub | - | ✓ | ✓ |
| Who's connected | - | - | ✓ |
| Join/leave events | - | - | ✓ |
| Participant & room metadata | - | - | ✓ |
| Admin controls (kick, close) | - | - | ✓ |
| Per-member streams | - | - | ✓ |
| Private messages (member-to-member) | - | - | ✓ |


## The model

Three objects:

- **`Room`** — the shared space. Created and managed on the server (the <Link href="#room-statics">`Room.*` statics</Link>), but anyone holding the room object — the server, or a client it was handed to — can observe its live membership, events, and message streams.
- **`LocalParticipant`** — the current user, returned by `join()`. Your identity in the room: you publish, send private messages, and update your metadata through it.
- **`RemoteParticipant`** — *everyone else*, as seen through a room: subscribe to one member's messages, watch their metadata, notice when they leave.

And three message lanes:

| Lane | Send | Receive | Typical use |
|---|---|---|---|
| Room-wide | `me.publish(data)` | `room.subscribe(cb)`, `member.subscribe(cb)` | Chat, game state, video frames |
| Private | `me.send(to, data)` | `me.listen(cb)` | DMs, invites, game moves |
| Room-authored | `Room.announce()`, `Room.send()` | `room.onAnnounce(cb)`, `me.listen(cb)` | System notices, rewards |

Two properties hold everywhere, so you never have to think about them:

- **One type, both sides.** A `Room` or `LocalParticipant` can be returned from a telefunction and used on the client as-is — everything below works identically on server and client unless marked otherwise.
- **The sender travels with the message.** Every received message carries its verified sender (`from.id`, `from.meta`) — stamped by the server, impossible to spoof, and never dependent on how fresh your local member list is. `from === null` means the room itself spoke (<Link href="#system-notices">room-authored</Link>).


## Quick start

A telefunction creates the room and hands it out; the client joins and chats:

```ts
// Lobby.telefunc.ts
// Environment: server

import { Room } from 'telefunc'

export async function onGetLobby() {
  return await Room.get('lobby') // created elsewhere with Room.create('lobby')
}
```

```ts
// Lobby.tsx
// Environment: client

import { onGetLobby } from './Lobby.telefunc'

const lobby = await onGetLobby()

lobby.onJoin((m) => console.log(`${m.meta.name} joined`))
lobby.subscribe((data, info, from) => console.log(`${from.meta.name}:`, data))

const me = await lobby.join({ name: 'Alice' })
await me.publish({ text: 'hello' })
```

> Like the built-in `Date`, `Room` is both a value and a type: the statics (`Room.get()`) and the instance type (`const lobby: Room`).

That's the whole core. The guides below cover the common tasks one at a time; the <Link href="#reference">reference</Link> and <Link href="#production">production notes</Link> come after.


## Guides

### Show who's here

`getParticipants()` gives you the member list; `onJoin`/`onLeave` keep it fresh; each member's `onUpdate` tracks their metadata:

```ts
for (const member of await room.getParticipants()) addToList(member)
room.onJoin((member) => addToList(member))
room.onLeave((member) => removeFromList(member.id))

function addToList(member) {
  render(member.id, member.meta)
  member.onUpdate((meta) => render(member.id, meta)) // e.g. name or score changed
}
```

Your own metadata: `me.setMeta({ name: 'Alice', score: 42 })` — a full replace that propagates to every observer in real time.

Presence is all a lurker costs: a connection that only observes membership never receives the room's messages — the message stream flows to a client only while it's subscribed (see <Link href="#delivery-and-cost">delivery & cost</Link>).

### Chat

Room-level for messages processed all the same way:

```ts
room.subscribe((data, info, from) => showMessage(from.meta.name, data))
await me.publish({ text: 'hello' })
```

Per-member when each member's stream needs its own handling:

```ts
room.onJoin((member) => {
  const decoder = createDecoder()
  member.subscribeBinary((data) => decoder.decode(data))
  member.onLeave(() => decoder.close()) // listeners die with the member — no unsubscribe needed
})
```

Both receive from the same stream: a member's `publish()` reaches room-level subscribers (with `from`) and that member's subscribers.

By default your own publishes come back to your own side too. Turn that off per participant when you don't want the echo (e.g. video): `join(meta, { selfDelivery: false })`.

### Private messages

`send()` delivers to exactly one participant. Privacy is transport-level: the message travels over the target's private inbox key — no other participant's connection ever receives it, and it never appears on `subscribe()` streams.

```ts
// Alice's client
me.listen((data, from) => showDm(from.meta.name, data))

// Bob's client
await bob.send(aliceId, 'meet me in room 2') // a RemoteParticipant works too
```

Sending to an unknown or departed participant rejects. `from` is the verified sender — `null` only for <Link href="#system-notices">room-authored</Link> messages.

### Moderate

`Room.guard()` attaches server-side policy to a room instance: it covers every membership granted through that instance — joins made on the server and joins made by the clients you handed the room to. Declare it in the granting telefunction, where you have <Link href="/getContext">`getContext()`</Link>:

```ts
// Chat.telefunc.ts
// Environment: server

export async function onJoinChat(roomId: string) {
  const { user } = getContext()
  const room = await Room.get(roomId)
  Room.guard(room, {
    // Gate room-wide messages (publish & publishBinary):
    onPublish: (from, data) => {
      if (isSpam(data)) throw new Error('blocked')
    },
    // Gate private messages, e.g. friends-only DMs:
    onSend: async (from, to) => {
      if (!(await db.areFriends(from.meta.userId, to.meta.userId))) throw new Error('not friends')
    },
  })
  return { room, me: await room.join({ name: user.name, userId: user.id }) }
}
```

When a guard throws, the sender's `publish()`/`send()` rejects with that error — on the client too, through the wire. Guards run on the server by construction (the statics don't exist in the browser build): authorization code never runs on the machines it polices.

The other moderation tools: observe without joining (`room.subscribe()` on the server), kick (`Room.removeParticipant()`), close (`Room.close()`) — see <Link href="#authorization">authorization</Link> for wiring those to admin users.

### System notices

The room itself can speak — no participant needed, and receivers can't confuse it with a member message:

```ts
// Server
await Room.announce('lobby', { type: 'maintenance', in: '5min' })   // to everyone
await Room.send('lobby', winnerId, { badge: 'first-blood' })        // to one participant
```

```ts
// Client
room.onAnnounce((data) => showBanner(data))     // announcements arrive here — never on subscribe()
me.listen((data, from) => {
  if (from === null) showSystemNotice(data)     // room-authored (Room.send())
  else showDm(from.meta.name, data)             // participant-authored (send())
})
```

### Video & binary streams

Two things make rooms carry media well: **binary rides per-publisher streams** — a client receives a member's binary only while subscribed to that member (or the whole room), and servers pull only the streams their clients watch — and `selfDelivery: false` keeps your own frames from echoing back. For rooms on Cloudflare, add `isolated: true` (see <Link href="#delivery-and-cost">delivery & cost</Link>):

```ts
// VideoChat.telefunc.ts
// Environment: server

export async function onJoinVideoRoom(roomId: string, name: string) {
  const videoRoom = await Room.get(`video:${roomId}`) // created with { isolated: true }
  const me = await videoRoom.join({ name }, { selfDelivery: false })
  return { me, videoRoom }
}
```

```ts
// VideoChat.tsx
// Environment: client

const { me, videoRoom } = await onJoinVideoRoom('demo', 'Alice')

captureAndEncode(camera, (frame) => me.publishBinary(frame))

for (const member of await videoRoom.getParticipants()) startDecoding(member)
videoRoom.onJoin((member) => startDecoding(member))

function startDecoding(member) {
  if (member.id === me.id) return
  const decoder = createDecoder()
  member.subscribeBinary((data) => decoder.decode(data)) // subscribing = the stream starts flowing
  member.onLeave(() => decoder.close())
}
```

Render only 9 of 500 cameras? Subscribe to those 9 members — the other 491 streams never cross the wire to you, and your server never even pulls them upstream.

### Load history, then go live

Rooms deliver **live** messages; history belongs in your database (retention, search, pagination — your rules). Two pieces: store every message as it's published, and on page load stitch history and the live stream together without losing anything.

**Store.** Give each message an ID at the sender, and persist in the `onPublish` guard — it runs exactly once per message, on the server, with the verified sender:

```ts
// Chat.telefunc.ts
// Environment: server

export async function onJoinChat(roomId: string) {
  const room = await Room.get(roomId)
  Room.guard(room, {
    onPublish: async (from, message) => {
      await db.messages.insert({ id: message.id, roomId, authorId: from.id, author: from.meta.name, ...message })
    },
  })
  return { room } // the client joins — its join ack fences the history read (below)
}

export async function onChatHistory(roomId: string) {
  return await db.messages.latest(roomId, 50)
}
```

**Replay.** Subscribe, join, then fetch history — that exact order is what makes the seam lossless:

```ts
// Chat.tsx
// Environment: client

const { room } = await onJoinChat('lobby')

const seen = new Set<string>()
const show = (message) => {
  if (seen.has(message.id)) return // the overlap — a message that made it into both
  seen.add(message.id)
  renderMessage(message)
}

room.subscribe((message) => show(message))                          // 1. declare the subscription
const me = await room.join({ name })                                // 2. the join ack is the fence
for (const message of await onChatHistory('lobby')) show(message)   // 3. the past — read after 1 is live

await me.publish({ id: crypto.randomUUID(), text: 'hi' })           // sender mints the ID
```

Why this is airtight:

- The subscription declaration (step 1) and the join request (step 2) travel the same ordered connection, so by the time `join()` resolves, the server has already activated your subscription — **the join ack doubles as a fence**.
- The history read (step 3) therefore starts strictly after the live stream did, and the store hook writes each message *before* it's published — so every message lands in at least one of the two sources. A message published between the steps lands in **both**, and the ID check drops the duplicate.
- The reverse order (fetch history, then subscribe) opens a gap instead: a message published in between lands in **neither**, and no dedup can recover it. Gaps are unrecoverable; overlaps are one `Set` lookup.

> Why not one telefunction call returning `{ room, history }`? Your subscription can only go live after that response returns — a history read inside the same call always precedes it, re-opening the gap. Closing it server-side would mean rooms retaining messages; message storage is exactly what stays in your database. The second call costs one concurrent round-trip on page load.

### Enforce capacity

`size` is a hint — Telefunc tracks it (`count`, `isFull`, `onFull()`) but never rejects a join. You decide, in the telefunction:

```ts
export async function onJoinLobby(name: string) {
  const lobby = await Room.get('lobby')
  if (lobby.isFull) throw new Error('room is full')
  return await lobby.join({ name })
}
```

`count` is exact at `Room.get()` (one key scan, no member reads) and stays live while the room is observed.


## Reference

### `Room.*` statics

The server-side entry point — like <Link href="/channel#broadcast">`Broadcast.*`</Link>. Clients get a room when a telefunction returns it.

| Method | Returns | Throws |
|---|---|---|
| `Room.create(id, options?)` | `Room` | If the room already exists |
| `Room.get(id)` | `Room` | If the room doesn't exist |
| `Room.guard(room, { onSend?, onPublish? })` | `void` | If called twice for one instance |
| `Room.join(id, meta?, options?)` | `LocalParticipant` | If the room doesn't exist |
| `Room.list()` | `RoomInfo[]` | - |
| `Room.update(id, options)` | `void` | If the room doesn't exist |
| `Room.close(id)` | `void` | If the room doesn't exist |
| `Room.removeParticipant(id, participantId)` | `void` | If the room or participant doesn't exist |
| `Room.announce(id, data)` | `void` | If the room doesn't exist |
| `Room.send(id, participantId, data)` | `void` | If the room or participant doesn't exist |

Options (for `Room.create()` and `Room.update()`):

```ts
type RoomOptions = {
  meta?: Record<string, unknown> // room metadata (default: {})
  size?: number                  // capacity hint (default: Infinity) — not enforced
  isolated?: boolean             // per-member text keys (default: false) — fixed at creation
}
```

- `Room.join(id, meta?, options?)` is the shorthand for `(await Room.get(id)).join(meta, options)` — and the cheapest join: it reads only the room's config, no member data at all.
- `Room.update()` does a **full replace**: omitted options reset to their defaults (e.g. omitting `size` resets it to `Infinity`) — except `isolated`, which is fixed at creation. Concurrent updates from different servers converge: the latest write wins, identically on every node.
- `Room.close()` disconnects all participants, fires `onClose()` on every observer, and removes the room. Afterwards `Room.get(id)` throws.

### `Room` instance

| Method | Description |
|---|---|
| `join(meta?, options?)` | Join the room. Returns your own <Link href="#localparticipant">`LocalParticipant`</Link>. Options: `{ selfDelivery?: boolean }`. |
| `getParticipants()` | All current participants — `Promise<RemoteParticipant[]>` (loads the member list on first need). |
| `getParticipant(id)` | One participant, or `null` if they're not a member — `Promise<RemoteParticipant \| null>`. |
| `subscribe(cb)` | Receive all participant messages: `(data, info, from)`. Returns an unsubscribe function. |
| `subscribeBinary(cb)` | Same, for binary messages. |
| `onJoin(cb)` / `onLeave(cb)` | A participant joined / left (or was removed): `(member)`. |
| `onUpdate(cb)` | The room was reconfigured via `Room.update()`: `(meta, prev)`. |
| `onAnnounce(cb)` | A room-authored announcement (`Room.announce()`) arrived: `(data, info)`. |
| `onEmpty(cb)` / `onFull(cb)` | The last participant left / the room reached capacity. |
| `onClose(cb)` | The room was closed — or, on the client, the connection is gone. |

State getters: `id`, `meta`, `size`, `count`, `isEmpty`, `isFull`, `isClosed`.

> **The member view loads once, on first need.** `Room.get()` is deliberately cheap: it knows the exact `count` immediately but doesn't read the member records. The first thing that needs them — `getParticipants()`, `getParticipant()`, or attaching a room-level listener — loads the view; from then on the room's event stream keeps it live and both lookups resolve from it without further I/O. `getParticipant()` resolving `null` means exactly one thing: not a member.

### `LocalParticipant`

Your own handle, returned by `join()`. Room-wide messages arrive on the room and on each `RemoteParticipant` — your `LocalParticipant` receives only the private messages addressed to you (`listen()`).

| Method | Description |
|---|---|
| `publish(data)` | Publish a message to the whole room. Returns a receipt (`{ key, seq, timestamp }`). |
| `publishBinary(data)` | Publish raw binary to the whole room. Returns a receipt. |
| `send(to, data)` | Send a private message to one participant (or their ID) — nobody else receives it. |
| `listen(cb)` | Receive private messages addressed to you: `(data, from)` — `from` is the verified sender, `null` for room-authored messages. Returns an unlisten function. |
| `setMeta(meta)` | Replace your metadata — propagates to all observers in real time. |
| `leave()` | Leave the room. |
| `onLeave(cb)` | You left — voluntarily, kicked, room closed, or disconnected. |

Read-only properties: `id`, `meta`, and `selfDelivery`.

- `selfDelivery` (default: `true`, set at `join()`): whether the messages you publish are delivered back to the room object on your side. Turn it off e.g. for video, where you don't want your own frames back.
- A participant lives exactly as long as its holder's connection: when the browser tab that holds it closes, navigates away, or loses its connection for good, the participant leaves the room automatically — observers see a normal leave.

### `RemoteParticipant`

Another room member, as seen through a room.

| Method | Description |
|---|---|
| `subscribe(cb)` | Receive only this member's messages: `(data, info)`. Returns an unsubscribe function. |
| `subscribeBinary(cb)` | Same, for binary messages — subscribing also starts that member's binary stream flowing to you. |
| `onUpdate(cb)` | This member's metadata changed: `(meta, prev)`. |
| `onLeave(cb)` | This member left the room (or was removed). |

Read-only properties: `id`, `meta`, and `joinedAt` (Unix epoch ms). A member's listeners are released when it leaves — cleanup in `onLeave` is enough, no unsubscribing needed.

### Senders

Every message callback receives its verified sender as `from: Sender` — `{ id, meta }`, stamped by the server, impossible for a client to fake. Normally `from` *is* the live `RemoteParticipant` (the same object `room.getParticipant(from.id)` returns), so you can use it directly.

In two situations there's no live object to hand you, and `from` is a plain `{ id, meta }` snapshot instead — same fields, same correct values:

- **You hold a participant but no room.** A telefunction can return just the participant — `return await Room.join(roomId, meta)` — without the room. Its `me.listen()` still tells you exactly who sent each private message; there's simply no room object around to look the sender up in.
- **A message outruns its sender's join.** Presence events and messages travel on separate streams so each can scale independently, and streams have no ordering *between* them. On the in-memory and <Link href="/redis">Redis</Link> transports this never materializes — their delivery is globally ordered — but backends that give every key its own coordinator (Cloudflare Durable Objects) can skew two streams by a few milliseconds. Delaying the message until the join lands would gate the fast lane on the slow one (and need a timeout policy — worse); dropping it would lose data. So Telefunc delivers immediately — the sender's identity is carried inside the message itself, and the live object takes over as soon as the join lands, typically one tick later.

Either way your code reads `from.id` and `from.meta` and never branches.

### Authorization

Admin operations live on the `Room.*` statics — not on the instance — so a room handed to clients carries no privileged methods. Wrap each admin operation in a telefunction that authorizes the caller:

```ts
// RoomAdmin.telefunc.ts
// Environment: server

import { Room, getContext } from 'telefunc'

export async function onKick(roomId: string, participantId: string) {
  const { user } = getContext()
  if (!user.isAdmin) throw new Error('unauthorized')
  await Room.removeParticipant(roomId, participantId)
}
```

<Warning>

**Room IDs are capabilities** — a telefunction that returns `await Room.get(roomId)` hands the caller the full room API: join, subscribe to all messages, read the member list. Derive room IDs from **authorized server-side context** (e.g. the user ID from <Link href="/getContext">`getContext()`</Link>), or verify access before returning the room:

```ts
export async function onJoinRoom(roomId: string, token: string) {
  const access = await db.verifyToken(token, roomId)
  if (!access) throw new Error('unauthorized')
  return await Room.join(roomId, { name: access.userName })
}
```

</Warning>


## Production

### Delivery and cost

Each lane travels on its own pub/sub stream, and every one is pay-for-what-you-consume:

| Lane | Who receives it | Cost |
|---|---|---|
| Control (joins, leaves, metadata, announcements) | Every observer | Tiny & low-rate — this is all a presence-only holder pays |
| Text (`publish`) | Only holders with message subscribers | `messages/s × size` per consuming connection — a busy chat (20 msg/s × 300 B) is ~6 KB/s |
| Binary (`publishBinary`) | Per publisher: only who subscribed to that member | Scales with what each client watches, not with room size |
| Private (`send`) | Only the target | Per message |

- Server-side relay buffers are byte-capped with FIFO eviction: a client that falls behind loses the oldest buffered messages first, and server memory stays bounded. Binary can never evict control events.
- Serializing a room to a client is O(1) — the member list streams separately, right behind the response.
- **`isolated: true`**: text moves to per-member keys too (binary always uses them). On platforms that map each pub/sub key to a single coordinator — Cloudflare Durable Objects — this removes publish contention for chatty rooms. Clients don't see the difference. Elsewhere, the default shared text key means fewer subscriptions.

### Consistency

Room state is event-driven and converges deterministically across servers:

- Presence (join/leave) events are idempotent — echoes and redeliveries are absorbed.
- Metadata changes carry an owner-issued revision — a stale or duplicated event can never overwrite a newer one.
- `Room.update()` is last-writer-wins with a deterministic tiebreak — concurrent updates from different servers converge to the same result on every node, whatever the arrival order.

### Crash-safe presence

Graceful departures (leave, kick, close, disconnect) propagate instantly as events. Against hard crashes, three layers:

1. The server owning a participant refreshes its liveness timestamp every 30s.
2. Members whose owner stopped refreshing are reaped — and their leave announced — on the next member-list read (2 minute threshold, sized for eventually-consistent stores).
3. Member records carry a native store expiry (Redis `PX`, Workers KV `expirationTtl`) as the backstop: even a room nothing ever reads again cannot retain ghosts.

### Multiple servers

A room keeps its state in a key-value store and sends its events over pub/sub, just like <Link href="/channel#broadcast">`Broadcast`</Link>:

- **Single server**: the default in-memory adapter works out-of-the-box.
- **Multiple servers**: install a cross-instance transport and every server sees the same rooms. <Link href="/redis">`@telefunc/redis`</Link> supports rooms out-of-the-box (state in Redis keys, events over Redis Pub/Sub, Cluster included), and so does the <Link href="/stream/cloudflare">Cloudflare integration</Link> (state in Workers KV, events over Durable Objects).
- **Custom transports**: implement the KV methods (`get()`, `set()`, `delete()`, `keys()`) on your `BroadcastTransport`, backed by a store all server instances can reach. Until then, room operations fail with a clear error.

## How it works

- **One key per lane.** Control events ride the room's key; text data rides its own key (per-member keys in isolated mode); binary rides per-publisher member keys; private messages ride per-member inbox keys that only the target's server subscribes to.
- **Lazy everything.** Servers subscribe upstream only to the lanes and members someone is actually consuming; clients receive only what they subscribed to; the member list loads on first need and streams to clients behind the response.
- **Sender identity in the envelope.** The sender's node stamps its verified `{ id, meta }` into every message, so delivery never waits on membership ordering — cross-lane races are a non-event.
- **Binary framing.** Binary messages are prefixed with the sender's 16-byte participant ID — fixed-size, no length field needed.
- **Crash-safe presence.** Liveness heartbeats + reap-on-read + native KV expiry (see <Link href="#crash-safe-presence">above</Link>).
