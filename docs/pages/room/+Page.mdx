`Room` adds multi-party **rooms** on top of <Link href="/channel">channels</Link>: presence, participant metadata, per-member streams, private messages, and admin controls. Reach for it whenever *who is connected* matters: chat, game lobbies, collaborative editing.

Here is a working room. A telefunction hands one out; the client joins, sees who is there, and chats:

```js
// Lobby.telefunc.js (server)
import { Room } from 'telefunc'

export async function onGetLobby() {
  return await Room.getOrCreate('lobby')
}
```
```js
// Lobby.js (client)
import { onGetLobby } from './Lobby.telefunc'

const lobby = await onGetLobby()

lobby.onJoin((who) => console.log(`${who.meta.name} joined`))
lobby.subscribe((msg, info, from) => console.log(`${from.meta.name}: ${msg.text}`))

const me = await lobby.join({ meta: { name: 'Alice' } })
await me.publish({ text: 'hello' })
```

Open it in two browser tabs and each sees the other join and speak. That is the whole feature; everything below is one task at a time.


## The three objects

- **`Room`** is the shared space. You create and administer it on the server through the <Link href="#room-statics">`Room.*` statics</Link>; anyone holding the room object observes its live membership, events, and messages.
- **`LocalParticipant`** is you, returned by `join()`. You publish, send private messages, and set your metadata through it.
- **`RemoteParticipant`** is everyone else, seen through a room: subscribe to one member, watch their metadata, know when they leave.

Return any of the three from a telefunction and use it on the client exactly as on the server. Every message you receive carries its verified sender (`from.id`, `from.meta`, `from.identity`), stamped by the server and impossible to spoof; `from === null` means the room itself spoke.

Rooms build on <Link href="/channel">channels</Link>. Drop to a channel when you only need a server-client pipe or topic pub/sub, with no presence or membership.


## Guides

### Show who's here

`getParticipants()` gives you the member list; `onJoin`/`onLeave` keep it fresh; each member's `onUpdate` tracks their metadata:

```js
for (const member of await room.getParticipants()) addToList(member)
room.onJoin((member) => addToList(member))
room.onLeave((member) => removeFromList(member.id))

function addToList(member) {
  render(member.id, member.meta)
  member.onUpdate((meta) => render(member.id, meta))
}
```

For UI frameworks, skip the manual `onJoin`/`onLeave`/`onUpdate` wiring. `onChange()` fires on any change, and `snapshot()` returns an immutable view of the whole room that keeps the same reference until something changes, which is what `useSyncExternalStore` wants:

```jsx
// React: the whole adapter
function useRoom(room) {
  return useSyncExternalStore(room.onChange, room.snapshot)
}
```

`snapshot()` is a flat list, so grouping is yours to shape. One user's tabs and reconnects share an `identity`; collapse them into one row when you want a by-user roster:

```js
const byUser = Map.groupBy(snapshot.participants, (p) => p.identity ?? p.id)
```

**Your own metadata.** `me.setMeta({ name: 'Alice', score: 42 })` replaces it wholesale; `me.setAttributes({ score: 42 })` merges by key (other keys keep their value; a key set to `undefined` is removed). Both propagate to every observer.

Metadata holds durable identity state: name, avatar, score. Ephemeral state like cursors and typing indicators belongs on `publish()` (see <Link href="#chat">Chat</Link>), which touches no storage.


### Chat

Room-level, one handler for every message whoever sent it:

```js
room.subscribe((data, info, from) => showMessage(from.meta.name, data))
await me.publish({ text: 'hello' })
```

Per-member, when each member's stream needs its own handling:

```js
room.onJoin((member) => {
  const decoder = createDecoder()
  member.subscribe((data) => decoder.push(data))
  member.onLeave(() => decoder.close()) // a member's listeners die with it
})
```

A member's `publish()` reaches both room-level subscribers (with `from`) and that member's subscribers.

By default your own publishes come back to your own side. Turn that off per participant when you don't want the echo: `join({ meta, selfDelivery: false })`.

**High-frequency updates** (cursors, live reactions) can flood a slow connection. Pass `{ coalesce: key }`, and while a publish with that key is still in flight, newer ones collapse into a single pending send that carries only the latest value:

```js
onCursorMove((pos) => me.publish({ pos }, { coalesce: 'cursor' }))
```


### Identify your users

Participant IDs are per-membership: the same person is a different participant in every room, tab, and reconnect. To correlate memberships, stamp an `identity` at join. It's server-assigned in the telefunction (a client `join()` can't claim one), travels with the member, and can't be spoofed:

```js
// Chat.telefunc.js
// Environment: server

export async function onJoinChat(roomId) {
  const { user } = getContext()
  const room = await Room.get(roomId)
  return { room, me: await room.join({ meta: { name: user.name }, identity: user.id }) }
}
```
```js
room.subscribe((data, info, from) => {
  if (from.identity === myUserId) return // one of my own tabs
})
await Room.removeParticipant(roomId, { identity: userId, reason: 'banned' }) // kick every tab at once
```

Read one user's presence without loading the roster, or act on them across rooms:

```js
// Server
const [me] = await Room.getParticipants(roomId, { identity: userId }) // their memberships (tabs); [] if offline
if (me?.meta.status === 'dnd') skipNotification()

// "Ban everywhere": your app knows a user's rooms (identity was assigned at join). Loop and kick each.
for (const { id } of await Room.list()) // or your own list of the user's rooms
  await Room.removeParticipant(id, { identity: userId, reason: 'banned' }) // idempotent: 0 matches is fine
```

<Warning>Metadata is display state, not authorization. `from.meta.role` (or `.team`, `.isAdmin`) is whatever that client last set, so never gate on it. Keep the trusted `identity`-to-role map server-side, in the telefunction where `identity` is stamped and `getContext()` is available, and check that instead. The rule: **`identity` is trusted, `meta` is not.**</Warning>


### Direct messages

`send()` delivers to one participant. No one else receives it, and it never shows up on `subscribe()`:

```js
// Alice
me.listen((data, from) => showDm(from.meta.name, data))

// Bob (by id, or by RemoteParticipant)
const { seq, timestamp } = await bob.send(aliceId, 'meet me in room 2')
```

`send()` resolves once the message is sequenced onto the recipient's inbox, so awaiting it waits for the hand-off, not just the local enqueue. Delivery is best-effort: the pub/sub underneath is at-most-once.

Pass `{ ack: true }` to wait for the recipient's handler and get its reply. The receipt gains a `response` (whatever their `listen` returned); it rejects if the handler throws or the recipient leaves first:

```js
const { response, seq, timestamp } = await bob.send(aliceId, { move: 'e4' }, { ack: true })
// Alice: me.listen((move) => rules.check(move) ? 'ok' : 'illegal') // her return is Bob's `response`
```

A plain `send()` reaches a live participant at most once, never retried or stored. It survives a brief disconnect (it lands on reconnect); once the participant has fully left it's gone, and a `{ identity }` send to an offline user is a no-op. For delivery that outlives a full disconnect, persist on send and redeliver on the next join, keyed by `identity` (stable across reconnects; the participant id is not):

```js
// Server
Room.guard(room, {
  onAfterSend: (from, to, data) => db.saveDm(to.identity, data), // persist on send
  onAfterJoin: async (member) => {                               // redeliver on (re)join
    for (const dm of await db.undeliveredDms(member.identity)) await Room.send(room.id, { id: member.id }, dm.data)
  },
})
```


### Moderate

`Room.guard()` attaches server-side policy to one room instance. It runs on every membership granted through that instance: your own `join()`, and every `join()`, `publish()`, and `send()` a client makes after you return the room from the telefunction. Declare it there, where `getContext()` is available:

```js
// Chat.telefunc.js
// Environment: server

export async function onJoinChat(roomId) {
  const { user } = getContext()
  const room = await Room.get(roomId)
  Room.guard(room, {
    onBeforeJoin: (member) => { if (banned.has(member.identity)) throw new Error('banned') },
    onBeforePublish: (from, data) => { if (isSpam(data)) throw new Error('blocked') },
    onBeforeSend: async (from, to) => { if (!(await areFriends(from.identity, to.identity))) throw new Error('not friends') },
  })
  return { room, me: await room.join({ meta: { name: user.name }, identity: user.id }) }
}
```

Each `onBefore*` runs before the operation commits; its first argument is the acting member, and throwing rejects the caller with that error, on the client too. A rejected join writes nothing. Each `onAfter*` (`onAfterJoin`, `onAfterSend`, `onAfterPublish`) runs once it commits, with the receipt (`{ seq, timestamp }`): the place to persist a message in its server-assigned order (see <Link href="#load-history-then-go-live">Load history</Link>).

<Warning>Guards ride the specific instance you called `Room.guard()` on. Retrieve the same room twice and you have two instances; a guard on one does not apply to the other. Attach guards in the telefunction that hands the room to clients: every membership a client opens rides that returned instance, so one `Room.guard()` covers them all. A plain server-side `Room.get()` elsewhere is unguarded by design, the same way `Room.announce()` is: it is your own trusted code.</Warning>

**Kicks carry their reason.** Every departure says why, and a kick's reason arrives with the removal:

```js
// Server
await Room.removeParticipant(roomId, { id: participantId, reason: 'be nice' })

// The kicked client
me.onLeave((cause) => {
  if (cause.type === 'removed') showBanner(`Kicked: ${cause.reason}`)
  else if (cause.type === 'disconnected') showReconnectHint()
})
```

`cause.type` is one of `'left'`, `'removed'`, `'closed'`, `'disconnected'`.

The other moderation tools: observe without joining (`room.subscribe()` on the server), kick (`Room.removeParticipant()`), close (`Room.close()`). Wire them to admin users through your <Link href="/permissions">permissions</Link>.


### System notices

The room itself can speak, and receivers can't confuse it with a member message:

```js
// Server
await Room.announce('lobby', { type: 'maintenance', in: '5min' }) // to everyone
await Room.send('lobby', { id: winnerId }, { badge: 'first-blood' }) // to one participant
```
```js
// Client
room.onAnnounce((data) => showBanner(data)) // announcements never arrive on subscribe()
me.listen((data, from) => {
  if (from === null) showSystemNotice(data) // room-authored (Room.send())
  else showDm(from.meta.name, data)         // participant-authored (send())
})
```


### Let the server play

`Room.announce()` and `Room.send()` let the room speak. A server that needs to *act* in a room, running an authoritative game loop or a bot, wants a real participant. Join one with `{ hidden: true }`, once, on the node that owns the loop:

```js
// When the match is created, on the node that will run it:
const room = await Room.create(matchId)
const authority = await room.join({ identity: 'authority', hidden: true }) // identity is trusted, not spoofable
authority.listen((cmd) => world.apply(cmd)) // commands arrive as DMs; the return is the ack reply
startGameLoop(matchId, authority)           // each tick: authority.publishBinary(worldState)
```

A hidden participant is a full `LocalParticipant`: `publishBinary()`, `listen()`, `send()`, `onDemand()` all work. It sits out of presence only. `count`, `isFull`, `getParticipants()`, `snapshot()`, and `onJoin`/`onLeave`/`onEmpty` ignore it, so capacity counts real players and `onEmpty` fires when the last *player* leaves while the authority stays seated:

```js
room.onEmpty(() => stopGameLoop(matchId)) // last player gone; the hidden authority doesn't hold the room open
```

Join as many as you need: a game authority, a moderation bot, a metrics sink, each with its own trusted `identity`. They are server-side only (a client `join({ hidden: true })` throws) and never visible to clients. Read them back on the server with `getParticipants({ hidden: true })`, keyed by `identity` (never `meta.role`, which any client can set). Hand a client the one it should talk to by returning it from the telefunction:

```js
// Match.telefunc.js (server)
export async function onJoinMatch(matchId, name) {
  const { user } = getContext()
  const room = await Room.get(matchId)
  const authority = (await room.getParticipants({ hidden: true })).find((p) => p.identity === 'authority')
  return { room, me: await room.join({ meta: { name }, identity: user.id }), authority }
}
```
```js
// Client
const verdict = await me.send(authority, { type: 'move', to: 'e4' }, { ack: true }) // command + await its reply
authority.subscribeBinary((frame) => world.apply(frame))                            // read its state
```

Two properties to design around:

- **Commands are best-effort unless you ack them.** A plain `me.send(authority, cmd)` is at-most-once (Redis and Cloudflare both; neither persists or retries). For a command that must land, `await me.send(authority, cmd, { ack: true })` waits for the handler and returns `{ response, seq, timestamp }`, or rejects.
- **One owner, no failover.** The authority and its loop live on the node that created them; membership and streams are distributed, the loop is not.


### Binary streams & tracks

`publishBinary()` / `subscribeBinary()` carry raw bytes: canvas deltas, audio snippets, file chunks, small-scale audio/video. Mic, camera, and screen share travel over one member's stream as *named tracks*, several substreams sharing one connection. Publish with `{ track }`; subscribe with `{ track }` to receive only that substream (`{ track: null }` is the default, unnamed track). Attach per-frame `meta` for whatever the decoder needs, a keyframe marker or a timestamp, and read it back on `info.meta`:

```js
captureAndEncode(camera, (frame, isKey) => me.publishBinary(frame, { track: 'camera', meta: { key: isKey } }))

member.subscribeBinary((data, { meta, track }) => video.decode(data, { key: meta?.key, track }), { track: 'camera' })
```

<Warning>Rooms move binary over the same reliable, ordered transport as text (WebSocket or SSE). That is right for binary *data* and for small or controlled-network A/V. It lacks what large-scale live video needs (congestion control, simulcast, jitter buffering), so for production multi-party video pair rooms, used for presence, chat, and signaling, with a WebRTC SFU for the media. A lower-latency, unreliable media lane is tracked in [telefunc#449](https://github.com/telefunc/telefunc/issues/449).</Warning>

**Render only 9 of 500 cameras?** Subscribe to those 9 members, and the other 491 streams never reach you; your server never fetches them at all. The same holds per track: stop watching a screen share and its bytes stop flowing to you.

**Pause the encoder when nobody's watching.** `onDemand` fires when demand for one of your tracks changes. `0` means nobody anywhere is watching; a later non-zero means a viewer returned (a coarse interest signal, not an exact viewer count):

```js
me.onDemand((track, count) => {
  if (track === 'screen') count === 0 ? encoder.pause() : encoder.resume()
})
```

Each `publishBinary()` receipt also reports `receivers`, the track's live subscription count at that moment (`0` means nobody anywhere wants it). Use it to react while you're actively publishing, and `onDemand` (above) to learn when to resume once you've paused.

**Seed late subscribers with a keyframe.** A subscriber that joins mid-stream can't apply your deltas until it gets a keyframe. Mark keyframes `{ retain: true }` and the server keeps the last one per track, replaying it to every new subscriber before any live frame, so a joiner syncs immediately with nothing to wire up:

```js
me.publishBinary(keyframe, { track: 'camera', meta: { key: true }, retain: true }) // kept for late joiners
```

`{ retain: true }` works the same on `publish()`: the server keeps the last retained text message and hands it to late subscribers, the current state a joiner needs, like a game phase or a pinned notice. Last write wins per lane; the retained value is dropped when its publisher leaves or the room closes, never on a timer, like MQTT retained messages.

Every binary frame also carries `info.seq` (a strict per-track counter) and `info.timestamp`, assigned centrally like text, so you rarely pack your own sequence number or delta-baseline id into the payload.


### Load history, then go live

Rooms deliver *live* messages; history belongs in your database, where retention, search, and pagination are your rules. Store each message as it's published, then load history and go live in one call.

**Store** in the `onAfterPublish` hook. It runs once per message, on the server, after the message is sequenced, so it carries the verified sender and the message's authoritative order (`info.seq`, `info.timestamp`):

```js
// Chat.telefunc.js
// Environment: server

export async function onJoinChat(roomId) {
  const room = await Room.get(roomId, { tail: true }) // relay live messages from now
  Room.guard(room, {
    onAfterPublish: async (from, message, info) => {
      await db.messages.insert({ ...message, roomId, authorId: from.identity, seq: info.seq, at: info.timestamp })
    },
  })
  const history = await db.messages.latest(roomId, 50) // read after tailing began, ordered by seq
  return { room, history }
}
```

`{ tail: true }` starts buffering the room's live messages the moment the telefunction returns the room, and the client holds them until your first `subscribe()`. So the history you read *after* can't miss a message published meanwhile, and where history and the live tail overlap, your render skips ids it has already shown (the `seen` set below):

```js
// Chat.js
// Environment: client

const { room, history } = await onJoinChat('lobby')

const seen = new Set()
const show = (m) => { if (!seen.has(m.id)) { seen.add(m.id); render(m) } }

for (const m of history) show(m)   // the past
room.subscribe(show)               // flushes the held live tail, then stays live
```

Order both the stored history and the live tail by `seq`, the strict per-key counter every message carries, so they read as one timeline. `seq` and `timestamp` are assigned centrally (Redis, or the Cloudflare key authority), never a per-node clock, so the order holds across nodes.


### Switching rooms

Membership is per room, so switching is `leave()` then `join()`:

```js
await current?.leave()
current = await nextRoom.join({ meta: { name } })
```

Publishing to a room you've already left throws (`Participant has left the room`).


### Enforce capacity

`size` is a hint. Telefunc tracks it (`count`, `isFull`, `onFull()`) but never rejects a join. You decide, in the telefunction:

```js
export async function onJoinLobby(name) {
  const lobby = await Room.get('lobby')
  if (lobby.isFull) throw new Error('room is full')
  return await lobby.join({ meta: { name } })
}
```

`count` is exact at `Room.get()` and stays live while the room is observed.


### Beyond one room

Unread counts, room discovery, and subgroups all live one level up from a single room, and each is just another room or a query against a database you already have.

- **Unread badges** are a `messages-since(lastRead)` query against the store you write to in `onAfterPublish`. To notify a user about a room they *aren't* currently watching, give each user their own room that they stay subscribed to, and `Room.announce(userRoom, { roomId })` when a message arrives, so their sidebar keeps one subscription open instead of one per room.
- **A room directory** is itself a room. Clients watch a `lobby` room; creating or closing a room calls `Room.announce('lobby', { created: id })` or `{ closed: id }`. Waiting clients hear about it right away, with no polling.
- **Subgroups and team chat** are separate rooms. A team, a breakout, or a private thread each has its own membership and guards, so a message sent there never reaches anyone outside it. A single telefunction can return several rooms at once (e.g. `match` and `match:red`). To message a few people instead of a standing group, use `Room.send(id, { identity }, data)`.


## Reference

### Room statics

The server-side entry point. Clients get a room when a telefunction returns it.

| Method | Returns | Throws |
|---|---|---|
| `Room.create(id, options?)` | `Room` | If the room already exists |
| `Room.get(id, options?)` | `Room` | If the room doesn't exist |
| `Room.getOrCreate(id, options?)` | `Room` | - |
| `Room.guard(room, { onBefore*?, onAfter*? })` | `void` | If called twice for one instance |
| `Room.join(id, options?)` | `LocalParticipant` | If the room doesn't exist |
| `Room.list({ prefix? }?)` | `RoomInfo[]` | - |
| `Room.update(id, options)` | `void` | If the room doesn't exist |
| `Room.close(id)` | `void` | If the room doesn't exist |
| `Room.removeParticipant(id, target)` | `void` | Unknown participant `{ id }` |
| `Room.announce(id, data)` | `void` | If the room doesn't exist |
| `Room.send(id, target, data)` | `void` | If the room or participant doesn't exist |
| `Room.getParticipants(id, target?)` | `ParticipantSnapshotView[]` | If the room doesn't exist |

```ts
type RoomOptions = {
  meta?: Record<string, unknown> // room metadata (default: {})
  size?: number                  // capacity hint (default: Infinity), not enforced
  isolated?: boolean             // per-member text keys (default: false), fixed at creation
}
```

- `Room.get(id, { tail: true })` starts relaying live messages as soon as the room is returned to a client (see <Link href="#load-history-then-go-live">Load history</Link>).
- `Room.update()` replaces the fields you provide and keeps the rest (`isolated` is fixed at creation).
- `Room.removeParticipant(id, target)` and `Room.send(id, target, data)` take one participant ref for `target`: `{ id }` for a single membership (throws when unknown), or `{ identity }` for every membership of an identity at once (an idempotent sweep or fan-out). `removeParticipant` also carries its `reason` in that same object: `{ id, reason? }` or `{ identity, reason? }`.
- `Room.getParticipants(id, target?)` is a server-side point-in-time read (no live view, no subscription). Omit `target` for the whole roster; pass `{ identity }` to read one user's memberships (their open tabs), the cheap "is this user online" check that doesn't load the roster. `[]` for an absent identity.
- Typed metadata: `Room.get<ChatMeta, MemberMeta>(id)` types `room.meta`, `join`/`setMeta`, and `from.meta` everywhere; `Room.list<ChatMeta>()` types each `RoomInfo.meta`. These type parameters are unchecked assertions you supply; Telefunc trusts them and doesn't validate the shape.

### `Room`

| Method | Description |
|---|---|
| `join(options?)` | Join; returns your `LocalParticipant`. Options: `{ meta?, selfDelivery?, identity?, hidden? }` (`identity` and `hidden` are server-side only). |
| `getParticipants(options?)` / `getParticipant(id)` | The member list / one member (or `null`). `getParticipants({ hidden: true })` reads the off-presence participants instead (see <Link href="#let-the-server-play">Let the server play</Link>). |
| `subscribe(cb)` | All participant messages: `(data, info, from)`. Returns an unsubscribe. |
| `subscribeBinary(cb, { track? }?)` | Same, for binary, optionally one track. `info` carries `track` and `meta`. |
| `onJoin(cb)` / `onLeave(cb)` | A participant joined / left: `(member)` / `(member, cause?)`. |
| `onUpdate(cb)` | The room was reconfigured: `(meta, prev)`. |
| `onAnnounce(cb)` | A room-authored announcement arrived. |
| `onEmpty(cb)` / `onFull(cb)` / `onClose(cb)` | Last participant left / reached capacity / room closed. |
| `onChange(cb)` / `snapshot()` | One change signal plus immutable view: the `useSyncExternalStore` pair. |

State getters: `id`, `meta`, `size`, `count`, `isEmpty`, `isFull`, `isClosed`. Counts and presence reflect real players only; off-presence participants are read separately with `getParticipants({ hidden: true })`.

### `LocalParticipant`

Your own handle, from `join()`. Room-wide messages arrive on the room and each `RemoteParticipant`; your `LocalParticipant` receives only the private messages addressed to you.

| Method | Description |
|---|---|
| `publish(data, { coalesce?, retain? }?)` | Publish to the whole room. `coalesce` conflates a same-key burst (see <Link href="#chat">Chat</Link>); `retain` keeps it as the room's last message for late subscribers. |
| `publishBinary(data, { track?, meta?, retain? }?)` | Publish raw binary. `retain` keeps the last frame per track for late subscribers (see <Link href="#binary-streams-tracks">keyframes</Link>). The receipt's `receivers` is the live subscription count (`0` = nobody anywhere). |
| `send(to, data)` | Private message to one participant (or their ID). Resolves with the delivery receipt `{ seq, timestamp }` (best-effort hand-off). |
| `send(to, data, { ack: true })` | Confirmed send: waits for the recipient's `listen` handler and resolves with its return (the reply), rejecting if it throws or the recipient leaves. The request/response twin of the channel `send({ ack: true })`. |
| `listen(cb)` | Receive private messages: `(data, from)`, where `from` is `null` for room-authored. Return a value to reply to a `send(…, { ack: true })` sender. |
| `setMeta(meta)` / `setAttributes(partial)` | Replace / merge your metadata. |
| `onDemand(cb)` | `(track, count)` when demand for one of your tracks changes; `count === 0` means nobody watching. |
| `leave()` / `onLeave(cb)` | Leave / observe your own departure: `cause.type` is `'left' \| 'removed' \| 'closed' \| 'disconnected'`. |

Read-only: `id`, `meta`, `identity`, `selfDelivery`. A participant leaves automatically when its holder's connection is gone (`cause: 'disconnected'`).

### `RemoteParticipant`

Another member, seen through a room.

| Method | Description |
|---|---|
| `subscribe(cb)` / `subscribeBinary(cb, { track? }?)` | Receive this member's messages. Binary subscribing starts that member's stream flowing to you. |
| `onUpdate(cb)` / `onLeave(cb)` | This member's metadata changed / this member left. |

Read-only: `id`, `meta`, `identity`, `joinedAt`. Cleanup in `onLeave` is enough; a member's listeners are released when it leaves.

### Senders

Every message callback receives its verified sender as `from`: `{ id, meta, identity }`, stamped by the server, impossible to spoof. When your room view already knows the sender, `from` is their live `RemoteParticipant`. Otherwise (say, a message that arrived just before its sender's join) it's a plain object with the same `id`, `meta`, and `identity`. Either way the fields are identical, so you read `from.id` and `from.meta` without special-casing. `from === null` only for room-authored messages.


## Production

Rooms work across multiple server nodes out of the box with <Link href="/redis">`@telefunc/redis`</Link> and the <Link href="/stream/cloudflare">Cloudflare</Link> integration.

- **Pay for what you consume.** Presence-only observers never receive the room's messages; text and binary alike flow only from the members you subscribe to, and are fetched only while someone wants them.
- **Crash-safe presence.** A clean `leave()` shows up everywhere at once. A crash can't: the node holding each connection refreshes its members every 30s, and any member that stops being refreshed is removed and its departure announced, with the store's own key-expiry as a final backstop, so a crashed node leaves no ghosts.
- **Tuning presence latency.** A silently-dropped connection is held for <Link href="/channel-config">`config.channel.reconnectTimeout`</Link> before its members leave, so a brief blip does not flap presence. Lower it for snappier away-detection, raise it to ride out flaky mobile networks.
- **Deterministic convergence.** Metadata and config updates land in the same final state on every node, no matter what order they arrive in.
- **`isolated: true`** routes each member's `publish()` messages through their own pub/sub key instead of one key shared by the whole room. On platforms that map each key to its own coordinator (e.g. Cloudflare Durable Objects), that removes the contention of an entire room publishing through a single key; elsewhere it makes no difference.

Every inbound client message is capped by <Link href="/channel-config">`config.channel.messageLimit`</Link> (default 16 MiB); large payloads belong on <Link href="/stream">streams</Link>.
