Live database queries — end a read with `.live()`, and a client showing its rows fetches them again when a write changes them.

<PoweredByTelefuncStream pkg="live" />

## Install

```bash
npm install @telefunc/live
```

Wrap your database once, where your app creates it:

```ts
// database.ts
// Environment: server

import { drizzle } from 'drizzle-orm/node-postgres'
import { liveDrizzle } from '@telefunc/live/drizzle'
import pg from 'pg'

export const db = liveDrizzle(drizzle({ client: new pg.Pool({ connectionString }) }))
```

```ts
// database.ts
// Environment: server

import { Kysely, PostgresDialect } from 'kysely'
import { liveKysely } from '@telefunc/live/kysely'
import pg from 'pg'

const pool = new pg.Pool({ connectionString })
export const db = liveKysely(new Kysely<Database>({ dialect: new PostgresDialect({ pool }) }), pool)
```

```ts
// database.ts
// Environment: server

import postgres from '@prisma/orm-postgres/runtime'
import { livePrisma } from '@telefunc/live/prisma'
import pg from 'pg'

const pool = new pg.Pool({ connectionString })
export const db = livePrisma(postgres({ contract, pg: pool }), pool)
```

> Kysely and Prisma don't expose the pool they use: pass it as the second argument.

> The database client is a `pg.Pool` or `pg.Client`, a postgres.js `sql`, or a PGlite database, on Postgres 17 and above. Wrap it before its first query.

> There isn't any other setup: Telefunc finds `@telefunc/*` packages in your `package.json` and auto-loads them.


## Usage

End a read with `.live()` and return it:

```ts
// TodoList.telefunc.ts
// Environment: server

import { eq } from 'drizzle-orm'
import { db } from './database'
import { todos } from './schema'

export async function onGetTodos(userId: number) {
  return await db.select().from(todos).where(eq(todos.userId, userId)).orderBy(todos.id).live()
}

export async function onAddTodo(userId: number, text: string) {
  await db.insert(todos).values({ userId, text })
}
```

The same read with Kysely and with Prisma:

```ts
await db.selectFrom('todos').selectAll().where('userId', '=', userId).orderBy('id').live()
await db.orm.public.Todo.where({ userId }).orderBy((todo) => todo.id.asc()).live()
```

`.live()` runs the query and resolves to a `Live<Todo[]>`: the rows are its `data`. Reads without `.live()`, and writes, run as before.

> Forgetting `.live()` is a type error where the client uses the telefunction: `live()` and `watch()` below take a telefunction returning a `Live`.

> Calling `onGetTodos()` yourself gives the rows once, in `data`. To follow them, use `live()` or `watch()`.

### With TanStack Query

```tsx
// TodoList.tsx
// Environment: client

import { useQuery } from '@tanstack/react-query'
import { live } from '@telefunc/live/tanstack-query'
import { onGetTodos } from './TodoList.telefunc'

const { data: todos } = useQuery({
  queryKey: ['todos', userId],
  queryFn: live(onGetTodos, userId),
})
```

`todos` is the rows. The query refetches when a write changes the rows `onGetTodos()` read.

> `live()` wraps the `queryFn` and imports only `@tanstack/query-core`, no framework adapter. Its tests use React.

> A query rendered on the server shows its rows in the HTML, then fetches once more in the browser to go live, whatever its `staleTime`.

### Without a library

```ts
// TodoList.ts
// Environment: client

import { watch } from '@telefunc/live/client'
import { onGetTodos } from './TodoList.telefunc'

const stop = watch(onGetTodos, [userId], (todos) => render(todos))
```

`watch()` calls the telefunction, passes the rows to your callback, and calls it again each time they change. Call `stop()` when you no longer show them.

> At most one call runs at a time: changes arriving while it runs lead to one more call after it.

> On the server (SSR), `watch()` does nothing: it starts in the browser.

### Derived values

Compute a value from live values with `derived()`:

```ts
// TodoList.telefunc.ts
// Environment: server

import { derived } from '@telefunc/live'
import { eq } from 'drizzle-orm'
import { db } from './database'
import { todos } from './schema'

export async function onGetOpenCount(userId: number) {
  const rows = await db.select().from(todos).where(eq(todos.userId, userId)).live()
  return derived(() => rows.data.filter((todo) => !todo.done).length)
}
```

The derived value changes when a value its callback read changes.

> `derived()` runs the callback once. When a value it read changes, the client calls your telefunction again.


## What refetches

A client refetches when a committed write, through a wrapped database, changes rows its query returned or could return:

- A write to another user's rows doesn't refetch `onGetTodos(userId)`.
- A row sorting past the last row of a `limit` doesn't refetch the page.
- A rolled-back transaction refetches nothing; a committed one refetches once its `COMMIT` succeeds.
- A write also changes the tables its triggers, rules, column defaults and foreign key actions (`on delete cascade`) write to. When the schema doesn't say which (a rule, a call to a function written in SQL or PL/pgSQL, SQL built at run time), the tables the transaction locked do: they're read right before its `COMMIT` (a lone write runs in a transaction for it), and every query of those tables refetches.

When `@telefunc/live` can't tell whether a write changed the result (a function call in the query, a statement it doesn't follow, a write of more than 10,000 rows), it refetches.

> A write to a table your database role can't `SELECT` in full, or any write after a statement that may change a session's role (`SET ROLE`, `SET SESSION AUTHORIZATION`, `RESET ALL`, `DISCARD`, a `DO` block, a procedure), refetches every query of the tables it writes.

> The refetch is an ordinary call of your telefunction: its <Link href="/permissions">permission checks</Link> run again, and no row is sent to a client otherwise.

> Writes that don't go through your app — another app, a migration, `psql` — aren't seen.


## Under load

A query that keeps changing refetches at most every 100 ms, one refetch at a time, and its last change is always fetched.

When many queries change at once, for example a public feed, the server tells clients to refetch as fast as it can serve them: right away while it has time to spare, in turn while it's busy. Writes stay fast, and results update as often as the server can afford.

> Identical queries (same SQL, same parameters) refetching at the same time run once on the database. Your telefunction still runs for each client, with its permission checks. A query calling a volatile function, such as `random()` or `nextval()`, runs for each client.

> After a statement that may change a session setting (`SET`, `set_config()`, a `DO` block, a procedure or a function of yours), identical queries no longer share a run: a setting can change what a query returns.

> Bun and Deno don't report how busy the server is: there, clients are told right away.


## Multiple servers

On several servers, pass a transport that carries the changes to the other servers, for example Redis:

```ts
// database.ts
// Environment: server

import IORedis from 'ioredis'
import pg from 'pg'
import { drizzle } from 'drizzle-orm/node-postgres'
import { DefaultBroadcastAdapter } from 'telefunc'
import { RedisTransport } from '@telefunc/redis'
import { liveDrizzle } from '@telefunc/live/drizzle'

const transport = new DefaultBroadcastAdapter(new RedisTransport({ redis: new IORedis(redisUrl) }))
export const db = liveDrizzle(drizzle({ client: new pg.Pool({ connectionString }) }), { transport })
```

> `liveKysely()` and `livePrisma()` take it as their third argument: `liveKysely(db, pool, { transport })`.

> Without `transport`, a write is seen by the server that made it only.

> A message lost on the way refetches every query reading the table it was about.
