**Environment**: server.

<TelefuncStreamBeta />

```ts
// Environment: server

import { config } from 'telefunc'

config.channel = {
  reconnectTimeout: 60_000,  // Hold channels open after disconnect (ms)
  pingInterval: 5_000,       // Client ping interval (ms)
  connectTtl: 15_000,        // Wait for client to connect to new channel (ms)
  allowedOrigins: [],        // Origins of other sites' pages that may open a WebSocket
  maxMemory: '1g',           // Memory all channels may hold queued (bytes or '512m')
}
```

> This is the **server-side** `config.channel` — a separate object from the **client-side** <Link href="/transport"><code>config.channel.transports</code></Link> (`telefunc/client`).

> `maxMemory` is the most all channels together may hold queued on the server: messages and broadcasts not yet delivered to a client, messages your listeners are still handling, and the uploaded files a telefunction hadn't read yet when it returned. It defaults to a quarter of the memory the process reports (1 GiB fallback, 64 MiB on Cloudflare). Channels share it as they need it; as it fills, channels holding more than their share are limited first. By default, one channel holds at most 320 MiB of it. See <Link href="/channel#errors" /> for what a channel past its limit gets.

> **What to tune**: the defaults suit typical stream use cases; tune these only if you run into one of the issues below:
> - Slow/flaky clients dropping with `NetworkError` (`isChannel: true`) → raise `reconnectTimeout` (how long the server holds a channel open while a client is gone).
> - `ChannelOverflowError` → `await` your `send()`s; if it closed the channel, recreate it or rejoin, see <Link href="/channel#errors" />.
> - Want to use less memory → lower `maxMemory`.
> - WebSocket for pages on another origin than your server → see <Link href="/transport#websocket" />.
