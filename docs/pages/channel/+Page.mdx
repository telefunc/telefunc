The following low-level **primitives** enable all kinds of <Link href="/stream">stream</Link> use case.

- <Link href="#new-channel"><code>new Channel()</code></Link> — direct messages between one server and one client.
- <Link href="#broadcast"><code>Broadcast</code></Link> — a keyed pub/sub bus (`publish()`/`subscribe()`), server-side.
- <Link href="#new-broadcastchannel"><code>new BroadcastChannel()</code></Link> — broadcast also on the client-side.

> You can use them for one-way streams (aka streaming) as well as two-way streams (aka real-time):
> - Chat rooms
> - Live feeds (sports scores, stock tickers)
> - Collaborative editing
> - Multiplayer games
> - Live dashboards & metrics
> - Notifications & activity feeds

> For short-lived callbacks (e.g. progress updates), <Link href="/stream#callback">function passing</Link> is usually simpler.

> By default, channels and broadcasts use [SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) and work without extra server setup. When <Link href="/transport#channel-transport">WebSocket is enabled</Link>, the client starts on SSE and seamlessly upgrades to WebSocket in the background.

> **Needs a long-running server.** A channel holds a connection open for its entire lifetime, so channels and broadcasts don't work on serverless platforms that enforce a short time limit on connections (e.g. Vercel, AWS Lambda). See <Link href="/stream/cloudflare" /> for using channels on Cloudflare Workers, and <Link href="/stream/scale" /> for running multiple server instances.

> For channel configurations, see:
> - <Link href="/channel-config" />
> - <Link href="/transport" />


## `new Channel()`

It creates a two-way message pipe between the server and the one client that called the telefunction.

Simple example:

```js
// Clock.telefunc.js
// Environment: server

import { Channel } from 'telefunc'

export async function onClock() {
  const channel = new Channel()
  channel.onOpen(async () => {
    while (!channel.isClosed) {
      await channel.send(Date.now())
      await new Promise((resolve) => setTimeout(resolve, 1000))
    }
  })
  return { channel: channel.client }
}
```

> The server returns `channel.client`: the client gets the same API but with message directions flipped.

```ts
// Clock.tsx
// Environment: client

import { onClock } from './Clock.telefunc'

const { channel } = await onClock()
channel.listen((time) => console.log(time)) // 1700000000000, 1700000001000, ...
```

> The channel outlives the telefunction call: both ends can `send()` and `listen()` until either side closes it.

Two-way example:

```js
// Echo.telefunc.js
// Environment: server

import { Channel } from 'telefunc'

export async function onEcho() {
  const channel = new Channel()
  channel.listen((text) => channel.send(`echo: ${text}`))
  return { channel: channel.client }
}
```

```ts
// Echo.tsx
// Environment: client

import { onEcho } from './Echo.telefunc'

const { channel } = await onEcho()
channel.listen((text) => console.log(text)) // 'echo: Hello!'
channel.send('Hello!')
```

### `Channel` methods

| Method | Description |
|---|---|
| `send(data)` | Send a message. Await to apply backpressure. |
| `send(data, { ack: true })` | Send and await acknowledgement. |
| `sendBinary(data)` | Send binary data. Await to apply backpressure. |
| `sendBinary(data, { ack: true })` | Send binary and await acknowledgement. |
| `send(data, { lossy: true })` | Send where only the newest matters. A newer one may replace it. |
| `sendBinary(data, { lossy: true })` | Send binary where only the newest matters. |
| `listen(cb)` | Receive messages. Return a value to ack. Returns an unlisten function. |
| `listenBinary(cb)` | Receive binary. Return a value to ack. Returns an unlisten function. |
| `opened` | Promise that resolves on open; rejects if the channel ends before opening. |
| `closed` | Promise that resolves on clean close; rejects on failure. |
| `messages({ signal })` | Iterate `{ type: 'text' \| 'binary', data }` messages; abort to stop. |
| `onOpen(cb)` | Called when the channel opens. |
| `onClose(cb)` | Called when the channel closes. |
| `close()` | Close gracefully. |
| `abort(value?)` | Terminate immediately. |


> `listen()`, `listenBinary()`, `onOpen()` and `onClose()` accept `{ signal }` as their second argument. Aborting the signal removes that registration.

> Message listeners are called in registration order. A listener aborted by an earlier listener still gets that message.

### Receive messages in a loop

You can receive text and binary messages with an async loop:

```ts
// Clock.tsx
// Environment: client

import { onClock } from './Clock.telefunc'

const { channel } = await onClock()
const controller = new AbortController()
const { signal } = controller

try {
  for await (const m of channel.messages({ signal })) {
    console.log(m.type, m.data)
  }
} catch (err) {
  if (err !== signal.reason) throw err
}
```

> `controller.abort()` makes the loop throw `signal.reason`. Aborting or breaking out of the loop leaves the channel open.

> Listeners and active iterators each receive the incoming messages. An iterator starts listening at its first `next()` call.

> Without `{ ack: true }`, listener callbacks are called before the iterator's loop resumes. Their returned promises can still be pending.

> With `{ ack: true }`, callbacks and iterators are awaited in registration order. Advance past the message or stop iteration to let later listeners or iterators receive it.

> To return an acknowledgement value, use `listen()` or `listenBinary()`. An iterator supplies `undefined` when you advance past the message or stop iteration.

### TypeScript

`new Channel<ClientToServer, ServerToClient>()` takes two generic type parameters. Each is a function signature:
- The **argument** is the message type.
- The **return type** is the acknowledgement type (`void` if no ack).

```ts
// Room.telefunc.ts
// Environment: server

import { Channel } from 'telefunc'

type ServerMessage =
  | { type: 'system'; text: string }
  | { type: 'chat'; text: string }

type ClientMessage =
  | { type: 'join'; roomId: string }
  | { type: 'chat'; text: string }

type ClientToServer = (message: ClientMessage) => { accepted: true }
type ServerToClient = (message: ServerMessage) => { delivered: true }

export async function onJoinRoom() {
  const channel = new Channel<ClientToServer, ServerToClient>({ ack: true })

  channel.listen((message) => {
    if (message.type === 'join') {
      channel.send({ type: 'system', text: `Joined ${message.roomId}` })
      return { accepted: true }
    }
    channel.send({ type: 'chat', text: `echo: ${message.text}` })
    return { accepted: true }
  })

  return { channel: channel.client }
}
```

```ts
// Room.tsx
// Environment: client

import { onJoinRoom } from './Room.telefunc'

const { channel } = await onJoinRoom()

const unlisten = channel.listen((message) => {
  console.log(message.text)
  return { delivered: true }
})
// unlisten() to stop receiving

const ack = await channel.send({ type: 'join', roomId: 'general' })
ack.accepted // true
```

On the server, `send()` sends `ServerMessage`. On the client, `send()` sends `ClientMessage`. The `channel.client` type flips the message types.


### Acknowledgements

> Exactly one listener may return an acknowledgement value. Other listeners can observe the message and return `undefined`; two answers reject the send.

#### Channel-wide

```ts
const channel = new Channel<ClientToServer, ServerToClient>({ ack: true })

// Every send() returns a Promise with the listener's return value
const ack = await channel.send({ type: 'status', text: 'OK' })
```

#### Per-send

```ts
const channel = new Channel<ClientToServer, ServerToClient>()

// Opt in for a single send
const ack = await channel.send(data, { ack: true })

// Opt out on an ack-default channel
await channel.send(data, { ack: false }) // Promise<void>, no ack value

// Binary acks work the same way
const binaryAck = await channel.sendBinary(frame, { ack: true })
```

> A channel-wide `{ ack: true }` only applies to `send()` — `sendBinary()` always opts in per call, so pass `{ ack: true }` to each `sendBinary()` that needs an acknowledgement.

### Binary data

Send and receive raw binary alongside structured messages:

```ts
// Server
await channel.sendBinary(new Uint8Array([1, 2, 3]))
const unlisten = channel.listenBinary((data) => {
  console.log(data.byteLength)
  return { processed: true } // ack value (optional)
})
unlisten() // stop listening

// Client — same API
await channel.sendBinary(new Uint8Array(buffer))
channel.listenBinary((data) => {
  console.log(data.byteLength)
})

// Binary acks
const ack = await channel.sendBinary(frame, { ack: true })
```

A message the client sends must be under 64 MiB (32 MiB on Cloudflare with the `'ws'` transport). Over that, `send()`, `sendBinary()`, `publish()` and `publishBinary()` each throw at the call, before returning a promise, and the channel stays open.

### Backpressure

Without <Link href="#skip-to-the-newest">`lossy`</Link>, both `send()` and `sendBinary()` return a `Promise` that resolves when the receiver has capacity for more data. Await them in a loop to apply [backpressure](https://en.wikipedia.org/wiki/Backpressure_routing):

```ts
for (const frame of frames) {
  await channel.sendBinary(frame) // blocks until the receiver is ready
}
```

Fire-and-forget is also fine — a send goes out as soon as the connection has room, whether or not you await it:

```ts
channel.send({ type: 'ping' }) // no await needed
```

On the server, `send()` works the same whether the client is connected, offline, or hasn't opened the channel yet:

- It holds each message until the client confirms it, up to the default per-channel limit of 320 MiB, within <Link href="/channel-config">`maxMemory`</Link> for all channels. An awaited `send()` resolves once the client has room, so a sender that awaits builds no backlog.
- A `send()` past that rejects with `ChannelOverflowError`, and that message isn't delivered. The channel stays open, and later sends that fit go through.

So fire-and-forget can leave a gap: the client never gets a `send()` the server refused. Telefunc logs a warning at a channel's first refused `send()`.

To fix it, `await` each `send()` before the next, as in the clock example above, or send slower.

A publish waits for no subscriber, so a `BroadcastChannel` refuses none: the server holds up to the same per-channel limit for its client, within `maxMemory`, and past that the channel closes with `ChannelOverflowError`, unless it's lossy (see <Link href="#broadcast" />).

> On a slow uplink, a client's large message delays what that client sends after it, on all its channels, until the large message has gone up. A 4 MiB `sendBinary()` at 1 MiB/s delays them by about 3 s. Only later messages wait, and what the server sends keeps arriving. To keep later messages quick, split the large one into smaller sends.

> Over SSE, the server can't pause a message on its way to the client. Encoding adds a third, so 8 MiB at 1 MiB/s takes about 11 s. A later `send()` of up to 16 KiB on another channel goes as soon as that 8 MiB message is out, ahead of what's queued behind it. Every other later message from the server waits behind what's queued before it. What the client sends still reaches the server.

> A server's `close()` waits for the client's answer, up to its timeout of 5 s by default. When a message on its way takes longer, as the 8 MiB one above does, the `close()` times out: the channel ends on the server, and `onClose()` receives a `ChannelClosedError`. To avoid that, pass a longer timeout, such as `close({ timeout: 20_000 })`.

#### When held messages clear

| Held | Where | Limit | Clears |
|---|---|---|---|
| A channel's `send()`s | Server | 320 MiB per channel by default, within `maxMemory` | As the client confirms them, in batches, once its `listen()` callbacks are done, including the promises they return |
| A `BroadcastChannel`'s publishes | Server | See above, within `maxMemory` | As the client confirms them, in batches, once its `subscribe()` callbacks have returned. Their promises aren't awaited |
| A `BroadcastChannel`'s `messages()` loop | Where the loop runs | 2 MiB past its next message | As the loop reaches each message |

### Skip to the newest

Where only the newest message matters, such as a pointer's position, pass `lossy: true` to that send. A client that keeps up still gets every message. Once a message has waited about 600 ms past the connection's round trip, a newer one replaces those waiting, so a client that can't keep up gets the newest soon. This holds both ways, on the way to the client and on the client's own way up:

```ts
// Pointer.telefunc.ts
// Environment: server

import { Channel } from 'telefunc'

type Position = { x: number; y: number }
type PointerMove = (position: Position) => void

export async function onPointer() {
  const channel = new Channel<PointerMove, PointerMove>()
  channel.listen((position) => moveMyPointer(position))
  onOthersPointerMove((position) => channel.send(position, { lossy: true }))
  return { channel: channel.client }
}
```

```ts
// Pointer.tsx
// Environment: client

import { onPointer } from './Pointer.telefunc'

const { channel } = await onPointer()
channel.listen((position) => drawOthersPointer(position))
window.addEventListener('pointermove', (e) => channel.send({ x: e.clientX, y: e.clientY }, { lossy: true }))
```

> A send without `lossy` is never skipped, and nothing passes it: the lossy sends that arrive stay on the side of it they were sent on.

> A lossy send resolves at once, without waiting for the other end. `lossy` can't be combined with `ack: true`: a newer message may take its place, so it gets no answer.

> `lossy` skips what the connection couldn't carry. A slow `for await` loop over `messages()` still reads every message that arrived.

## `Broadcast`

`Broadcast` is a keyed pub/sub **bus**: a message published to a `key` reaches every subscriber of that `key` — server-side subscribers (via `Broadcast.subscribe()`) and clients bridged into the `key` (via <Link href="#new-broadcastchannel">`new BroadcastChannel()`</Link>). Publishers and subscribers are decoupled; all they share is the `key` string.

The static methods run purely on the server — no client, no handle, no lifecycle — and take the `key` as their first argument:

```ts
import { Broadcast } from 'telefunc'

// Publish to every subscriber of the key
Broadcast.publish('room:lobby', { text: 'Hello!' })

// Subscribe on the server
const unsub = Broadcast.subscribe('room:lobby', (msg, info) => {
  console.log(msg, info.seq)
})
```

`publish()` returns a receipt and `subscribe()` receives the same `info`:

```js
info.key        // 'room:lobby' — the broadcast key
info.seq        // monotonic sequence number for this key
info.timestamp  // server timestamp (Unix epoch ms)
```

`publish()` resolves to `info` once the message is accepted.

`seq` counts the publishes on a `key`, `publish()` and `publishBinary()` together. Each publish adds exactly 1, so a jump means a subscriber missed messages:

```ts
let lastSeq = null
Broadcast.subscribe('room:lobby', (msg, info) => {
  if (lastSeq !== null && info.seq > lastSeq + 1) console.warn(`Missed ${info.seq - lastSeq - 1} messages`)
  lastSeq = info.seq
})
```

> A subscriber sees only its kind of message: to check `seq` on a key that mixes text and binary, count `subscribe()` and `subscribeBinary()` together.

| Broadcast transport | Across server instances | After a restart |
|---|---|---|
| In-memory (default) | Each server has its own | Starts over when the server restarts |
| `@telefunc/redis` | One counter, so a message has the same `seq` on every instance | Continues across server restarts. Starts over at 1 if Redis loses its data |
| Cloudflare | One counter, so a message has the same `seq` everywhere | Continues |

> In memory, a key's counter lasts while the key has a subscriber on that server. Once the key has no subscriber left there, its next publish gets a `seq` above every one that server has issued.

Awaiting `publish()` doesn't wait for any subscriber's client to keep up: a client that falls behind a broadcast gets every message the server holds for it, and past that the channel closes with `ChannelOverflowError` (see <Link href="#errors">errors</Link>). Other channels on its connection wait behind what's held for it. Where only the newest message matters, make it <Link href="#skip-to-the-newest">lossy</Link>: a client that can't keep up then skips to the newest, and `info.seq` jumps over what it skipped.

A `subscribe()` callback's `async` work isn't awaited, on the page or on the server: the next message arrives whether or not your callback is done. Telefunc doesn't limit how many calls of your callback are unfinished, so if it can fall behind, limit them in your code.
For example, a callback that does an `await fetch()` for each message should queue them, and drop or merge what it can't keep up with.

> By default, broadcast is in-memory — messages only reach subscribers on the same server. This works out-of-the-box for single-server deployments.
>
> For <Link href="/stream/scale">scaling horizontally</Link>, you must configure `Broadcast` to publish across all server instances — see <Link href="/stream/scale#broadcast" />


## `new BroadcastChannel()`

`new BroadcastChannel({ key })` lets you broadcast from and to the client-side (whereas `Broadcast` is server-side only).

> It creates a `Channel` to the one client that received it, and bridges that client onto a `Broadcast` key.
>
> Return it from a telefunction and the receiving client can `publish()` / `subscribe()` on the key — every message reaches every member of the group (both client-side and server-side).


<Warning>

**Keys are capabilities** — anyone who knows the `key` joins the group. Secure a broadcast in one of two ways:
- **Guard the key**: derive it from **authorized server-side context** (e.g. the user ID from <Link href="/getContext">`getContext()`</Link>), never from client-side input.
- **Guard the payload**: whatever you `publish()` reaches every subscriber, so broadcast only non-sensitive data. That's how <Link href="/tanstack-query"><code>@telefunc/tanstack-query</code></Link> stays safe — it broadcasts only a *"refetch"* signal, and each client loads the actual data through its own authorized telefunction.

See also:
- <Link href="/stream#authorization" />
</Warning>

### Chat example

```ts
// Chat.telefunc.ts
// Environment: server

import { BroadcastChannel } from 'telefunc'

type ChatMessage = { user: string; text: string }

export async function onJoinChat(room: string, username: string) {
  const chat = new BroadcastChannel<ChatMessage>({ key: `chat:${room}` })

  chat.onOpen(() => {
    chat.publish({ user: 'system', text: `${username} joined` })
  })

  chat.onClose(() => {
    chat.publish({ user: 'system', text: `${username} left` })
  })

  return chat
}
```

> Unlike channels (`new Channel()`), no `.client` is needed: broadcast is symmetric — the same instance has the same message type on both ends (no directional flip).

```ts
// Chat.tsx
// Environment: client

import { onJoinChat } from './Chat.telefunc'

const chat = await onJoinChat('lobby', 'Alice')

// Receive messages published to the key, including this instance's own publishes
chat.subscribe((msg, info) => {
  console.log(`#${info.seq} ${msg.user}: ${msg.text}`)
})

// Publish to every subscriber of the key
chat.publish({ user: 'Alice', text: 'Hello!' })
```

### Receive broadcast messages in a loop

```ts
// Chat.tsx
// Environment: client

const controller = new AbortController()
for await (const message of chat.messages({ signal: controller.signal })) {
  console.log(message.type, message.data, message.info.seq)
}
```

> `messages()` works on both server and client. Each message includes the same `info` as a subscription callback. The loop follows the <Link href="#receive-messages-in-a-loop">channel loop's cancellation and close behavior</Link>.

> A publish doesn't wait for a slow loop. The loop holds up to 2 MiB of messages past its next one. Beyond that, the loop ends with `ChannelOverflowError`, on the server and on the client.

> `subscribe()`, `subscribeBinary()`, `onOpen()` and `onClose()` accept `{ signal }` after the callback. The static `Broadcast.subscribe()` and `Broadcast.subscribeBinary()` accept it too. Aborting removes that registration.

### Notifications

A per-user key with a subscribe-only client — the server returns a `BroadcastChannel` keyed to the user, and the client only listens:

```ts
// Notifications.telefunc.ts
// Environment: server

import { BroadcastChannel, getContext } from 'telefunc'

export async function onListenNotifications() {
  const context = getContext()
  const broadcast = new BroadcastChannel({ key: `notifications:${context.userId}` })
  // Send a toast to *all* clients matching the user id, i.e. on all the tabs of
  // all the user's devices.
  setTimeout(() => broadcast.publish('hello'), 1000)
  setTimeout(() => broadcast.publish('world'), 2000)
  return broadcast
}
```

```ts
// Notifications.tsx
// Environment: client

const broadcast = await onListenNotifications()
broadcast.subscribe((n) => showToast(n))
```

### Lossy broadcast

A `BroadcastChannel` made with `lossy: true` <Link href="#skip-to-the-newest">skips to the newest</Link> for every message, such as a price:

```ts
// Price.telefunc.ts
// Environment: server

import { BroadcastChannel } from 'telefunc'

export async function onWatchPrice(symbol: string) {
  return new BroadcastChannel<number>({ key: `price:${symbol}`, lossy: true })
}
```

```ts
// Price.tsx
// Environment: client

import { onWatchPrice } from './Price.telefunc'

const price = await onWatchPrice('ACME')
price.subscribe((value, info) => showPrice(value, info.seq))
```

> `info.seq` jumps over the messages a client skipped, and the server logs a warning once. A key is one stream: a newer message replaces an older one whoever published it, so give each value its own key, such as one per pointer.

> Without `lossy`, a client gets every message, and past what the server holds for it the channel closes with `ChannelOverflowError` (see <Link href="#broadcast" />). To catch up, load the state again and call the telefunction for a new channel.

### `BroadcastChannel` methods

| Method | Description |
|---|---|
| `opened` | Promise that resolves on open; rejects if the channel ends before opening. |
| `closed` | Promise that resolves on clean close; rejects on failure. |
| `messages({ signal }?)` | Receive text and binary messages with publish info in an async loop. |
| `publish(data)` | Publish to every subscriber of the key. Returns a receipt. |
| `subscribe(cb, { signal }?)` | Receive `(data, info)`. Returns an unsubscribe function. |
| `publishBinary(data)` | Publish raw binary to every subscriber. Returns a receipt. |
| `subscribeBinary(cb, { signal }?)` | Receive `(data, info)` for binary messages. Returns an unsubscribe function. |
| `onOpen(cb)` | Called when the channel opens. |
| `onClose(cb)` | Called when the channel closes. |
| `close()` | Close gracefully. |
| `abort(abortValue?)` | Terminate immediately. |

> The instance is bound to its `key`, so `publish(data)` / `subscribe(cb)` take no key. The static <Link href="#broadcast"><code>Broadcast.publish(key, data)</code></Link> / `Broadcast.subscribe(key, cb)` have no `onOpen` / `onClose` / `close` / `abort` since there's no instance to manage.


## `new BroadcastChannel()` VS `new Channel()`

### Fundamentally

The difference is what a message is addressed to: a channel message is addressed to *someone*, a broadcast message is addressed to *a topic* (the `key`).

A channel is a conversation, like a phone call: two fixed ends (the server and the one client that received the channel), private to them, ending when either side hangs up.

A broadcast is an announcement, like a radio frequency: whoever tunes in to the `key` receives everything published to it, members come and go, and the `key` belongs to no one.

Only the two ends of a channel can use it, while anything that knows a broadcast's `key` can join it. A channel ends when either side closes it, while a broadcast outlives any single member.

### Comparison

| | `new Channel()` | `new BroadcastChannel()` |
|---|---|---|
| Topology | One server ↔ one client | All members sharing a `key` (server and client) |
| Methods | `send()` / `listen()` | `publish()` / `subscribe()` |
| Delivery | The other end | Every subscriber of the `key`, including the publisher |
| Message type | Asymmetric:<ul><li>Two different types: `Channel<ClientMessageType, ServerMessageType>`</li><li>The server uses the `new Channel()` instance, and returns `channel.client` to the client</li></ul> | Symmetric:<ul><li>Same type for every member: `BroadcastChannel<MessageType>`</li><li>The server uses and returns the same `BroadcastChannel` instance</li></ul> |
| Message return | The other end's reply (if `{ ack: true }`) | A receipt: `{ key, seq, timestamp }` |
| Skip to the newest | Per send: `send(data, { lossy: true })` | Per channel: `new BroadcastChannel({ key, lossy: true })` |
| `close()` | Closes the channel for both ends | Detaches this member; the group lives on |
| Multi-server | <Link href="/stream/scale#sticky-sessions">Sticky sessions</Link> | <Link href="/stream/scale#sticky-sessions">Sticky sessions</Link> and a <Link href="/stream/scale#broadcast">broadcast transport</Link> |


## Errors

Telefunc silently handles rejected promises from `send()`, `sendBinary()`, `publish()` and `publishBinary()`. To observe a failure, `await` the call or use `.catch()`.

A call that can't start throws instead of rejecting: one on a closed channel, or a client's message over the size limit in <Link href="#binary-data" />. `.catch()` doesn't see that throw, so put a `try` around the call.

A channel closes when one of its ends closes or aborts it, and when its client stays gone longer than `reconnectTimeout`. A slow client doesn't close a `Channel`, and neither does a refused `send()`. One thing does: a client with so many `send(data, { ack: true })` or `publish()` calls waiting for their answers at once that the server can't hold even their refusals. The channel then closes with `ChannelOverflowError`. A `BroadcastChannel` also closes, with `ChannelOverflowError`, where its client would miss a message, and a <Link href="#lossy-broadcast">lossy</Link> one where the server can't hold even the newest message for its client.

Channels and broadcasts signal failure through four errors:

| Error | When | Channel state | Recovery |
|---|---|---|---|
| `Abort` | Either side called `abort(value)`, or a callback threw `Abort` | Closed | Inspect `err.abortValue` |
| `NetworkError` (`isChannel: true`) | The client stayed gone longer than `reconnectTimeout` | Closed | Auto-closed — recreate if needed |
| `ChannelClosedError` | `send()` on a closed channel | Closed | Recreate the channel |
| `ChannelOverflowError` (`send()`) | The message would pass the default per-channel limit of 320 MiB, or `maxMemory`. For a client's `send(data, { ack: true })`, also where the server can't hold the answer | **Open**; only that message is lost | `await` each `send()` before the next. Split a message past the per-channel limit: awaiting doesn't help it, and neither does `maxMemory`. Raise `maxMemory` only where all channels together hold too much |
| `ChannelOverflowError` (closed) | A `BroadcastChannel`'s client fell behind what the server holds for it; for a lossy one, the server couldn't hold even the newest message. For any channel, its client had so many `send(data, { ack: true })` or `publish()` calls waiting for their answers at once that the server couldn't hold even their refusals | Closed | Call its telefunction again, then pass `lossy: true`, `await` each acknowledged call before the next, or raise `maxMemory` |
| `ChannelOverflowError` (`messages()`) | Its loop fell over 2 MiB behind the publishes, past its next message, or `maxMemory` is held and it's behind | The loop ends, the broadcast stays open | Handle each message faster, or use `subscribe()` |
| `ChannelOverflowError` (`publish()`) | With no Redis or other transport installed, a `subscribe()` callback published more than 320 MiB before its first `await` | Open | Publish less from the callback |

> A graceful `close()` isn't an error (`onClose(err)` receives `undefined`).

## Reconnection

If the connection drops, Telefunc reconnects automatically and resumes existing channels and broadcasts:

- Messages sent while offline are held and delivered in order on reconnect, up to the default per-channel limit of 320 MiB, within <Link href="/channel-config">`maxMemory`</Link>.
- Messages lost in the disconnect are resent after reconnect, if the client is back within `reconnectTimeout`.
- Otherwise, the channel closes with `NetworkError`.
- A `BroadcastChannel` holds up to the default per-channel limit of 320 MiB of what's published while its client is away, and closes with `ChannelOverflowError` past that. A lossy one holds only the newest, and `info.seq` shows the jump.
- While its client is away, a `Channel` keeps the newest `lossy` send between two sends without `lossy`.
- `onOpen()` fires only on initial open, `onClose()` only on permanent close.

> Reconnection is automatic — you don't need to handle it in your application code.
