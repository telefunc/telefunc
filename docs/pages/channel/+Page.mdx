Use these <Link href="/stream">stream</Link> **primitives** to send live updates between your server and browser, or to broadcast updates to a group:

- <Link href="#new-channel"><code>new Channel()</code></Link> — direct messages between one server and one client.
- <Link href="#broadcast"><code>Broadcast</code></Link> — a keyed pub/sub bus (`publish()`/`subscribe()`), server-side.
- <Link href="#new-broadcastchannel"><code>new BroadcastChannel()</code></Link> — broadcast also on the client-side.

> Use <Link href="/room">`Room`</Link> for presence, private messages, and per-participant tracks.

> You can use them for one-way streams (aka streaming) as well as two-way streams (aka real-time):
> - Chat rooms
> - Live feeds (sports scores, stock tickers)
> - Collaborative editing
> - Multiplayer games
> - Live dashboards & metrics
> - Notifications & activity feeds

> For short-lived callbacks (e.g. progress updates), <Link href="/stream#callback">function passing</Link> is usually simpler.

> By default, channels and broadcasts use [SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) and work without extra server setup. When <Link href="/transport#channel-transport">WebSocket is enabled</Link>, the client starts on SSE and seamlessly upgrades to WebSocket in the background.

> **Needs a long-running server.** A channel holds a connection open for its entire lifetime, so run channels on a server that can keep connections open. See <Link href="/stream/cloudflare" /> for Cloudflare Workers and <Link href="/stream/scale" /> for multiple servers.

> For channel configurations, see:
> - <Link href="/channel-config" />
> - <Link href="/transport" />


## `new Channel()`

It creates a two-way message pipe between the server and the one client that called the telefunction.

Simple example:

```js
// Clock.telefunc.js
// Environment: server

import { Channel } from 'telefunc'

export async function onClock() {
  const channel = new Channel()
  const interval = setInterval(() => channel.send(Date.now()), 1000)
  channel.onClose(() => clearInterval(interval))
  return { channel: channel.client }
}
```

> The server returns `channel.client`: the client gets the same API but with message directions flipped.

```ts
// Clock.tsx
// Environment: client

import { onClock } from './Clock.telefunc'

const { channel } = await onClock()
channel.listen((time) => console.log(time)) // 1700000000000, 1700000001000, ...
```

> The channel outlives the telefunction call: both ends can `send()` and `listen()` until either side closes it.

> Pass `new Channel({ id })` to supply your own ID. The default is a random UUID.

Two-way example:

```js
// Echo.telefunc.js
// Environment: server

import { Channel } from 'telefunc'

export async function onEcho() {
  const channel = new Channel()
  channel.listen((text) => channel.send(`echo: ${text}`))
  return { channel: channel.client }
}
```

```ts
// Echo.tsx
// Environment: client

import { onEcho } from './Echo.telefunc'

const { channel } = await onEcho()
channel.listen((text) => console.log(text)) // 'echo: Hello!'
channel.send('Hello!')
```

### `Channel` methods

| Method | Description |
|---|---|
| `send(data)` | Send a message. Await to apply backpressure. |
| `send(data, { ack: true })` | Send and await acknowledgement. |
| `sendBinary(data)` | Send binary data. Await to apply backpressure. |
| `sendBinary(data, { ack: true })` | Send binary and await acknowledgement. |
| `send(data, { lossy: true })` | Send where only the newest message matters, such as a pointer's position: a receiver that falls behind skips to the newest. |
| `sendBinary(data, { lossy: true })` | Send binary where only the newest message matters. |
| `listen(cb)` | Receive messages. Return a value to ack. Returns an unlisten function. |
| `listenBinary(cb)` | Receive binary. Return a value to ack. Returns an unlisten function. |
| `messages({ signal })` | Receive text and binary messages in a `for await` loop. |
| `onOpen(cb)` | Called when the channel opens. |
| `onClose(cb)` | Called when the channel closes. |
| `onDisconnect(cb)` / `onReconnect(cb)` | Called when the other side becomes unreachable / is back. See <Link href="#reconnection" />. |
| `isConnected` | `true` from `onOpen` until `onClose`, except while the other side is unreachable. |
| `opened` | Promise that resolves when the channel opens. |
| `closed` | Promise that resolves when the channel has closed: with `null`, or with the error it ended with. |
| `close()` | Close gracefully. Resolves with `null` once closed, or with the error it ended with. |
| `abort(value?)` | Terminate immediately. |

> `onOpen()` and `onClose()` return a function that removes the callback. `listen()`, `listenBinary()`, `onOpen()` and `onClose()` also accept `{ signal }` as their second argument: aborting it removes the callback.


### TypeScript

`new Channel<ClientToServer, ServerToClient>()` takes two generic type parameters. Each is a function signature:
- The **argument** is the message type.
- The **return type** is the acknowledgement type (`void` if no ack).

```ts
// Room.telefunc.ts
// Environment: server

import { Channel } from 'telefunc'

type ServerMessage =
  | { type: 'system'; text: string }
  | { type: 'chat'; text: string }

type ClientMessage =
  | { type: 'join'; roomId: string }
  | { type: 'chat'; text: string }

type ClientToServer = (message: ClientMessage) => { accepted: true }
type ServerToClient = (message: ServerMessage) => { delivered: true }

export async function onJoinRoom() {
  const channel = new Channel<ClientToServer, ServerToClient>({ ack: true })

  channel.listen((message) => {
    if (message.type === 'join') {
      channel.send({ type: 'system', text: `Joined ${message.roomId}` })
      return { accepted: true }
    }
    channel.send({ type: 'chat', text: `echo: ${message.text}` })
    return { accepted: true }
  })

  return { channel: channel.client }
}
```

```ts
// Room.tsx
// Environment: client

import { onJoinRoom } from './Room.telefunc'

const { channel } = await onJoinRoom()

const unlisten = channel.listen((message) => {
  console.log(message.text)
  return { delivered: true }
})
// unlisten() to stop receiving

const ack = await channel.send({ type: 'join', roomId: 'general' })
ack.accepted // true
```

On the server, `send()` sends `ServerMessage`. On the client, `send()` sends `ClientMessage`. The `channel.client` type flips the message types.


### Acknowledgements

#### Channel-wide

```ts
const channel = new Channel<ClientToServer, ServerToClient>({ ack: true })

// Every send() returns a Promise with the listener's return value
const ack = await channel.send({ type: 'system', text: 'OK' })

// Opt out for a single send
await channel.send({ type: 'system', text: 'OK' }, { ack: false }) // Promise<void>, no ack value
```

#### Per-send

```ts
const channel = new Channel<ClientToServer, ServerToClient>()

// Opt in for a single send
const ack = await channel.send({ type: 'system', text: 'OK' }, { ack: true })

// Binary acks work the same way
const binaryAck = await channel.sendBinary(frame, { ack: true })
```

> A channel-wide `{ ack: true }` only applies to `send()` — `sendBinary()` always opts in per call, so pass `{ ack: true }` to each `sendBinary()` that needs an acknowledgement.

### Binary data

Send and receive raw binary alongside structured messages:

```ts
// Server
await channel.sendBinary(new Uint8Array([1, 2, 3]))
const unlisten = channel.listenBinary((data) => {
  console.log(data.byteLength)
  return { processed: true } // ack value (optional)
})
unlisten() // stop listening

// Client — same API
await channel.sendBinary(new Uint8Array(buffer))
channel.listenBinary((data) => {
  console.log(data.byteLength)
})

// Binary acks
const ack = await channel.sendBinary(frame, { ack: true })
```

### Backpressure

Both `send()` and `sendBinary()` return a `Promise` that resolves when the receiver has capacity for more data. Await them in a loop to apply [backpressure](https://en.wikipedia.org/wiki/Backpressure_routing):

```ts
for (const frame of frames) {
  await channel.sendBinary(frame) // blocks until the receiver is ready
}
```

For an occasional update, you can call `channel.send(data)` without waiting. See <Link href="/channel-config">the channel configuration</Link> for the memory budget and <Link href="#errors" /> for what happens when a backlog fills it.

### Skip to the newest

Pass `lossy: true` when only the latest value matters. A receiver that falls behind skips superseded values:

```js
// Pointer.js
// Environment: client

const onMove = ({ clientX, clientY }) => channel.send({ x: clientX, y: clientY }, { lossy: true })
window.addEventListener('pointermove', onMove)
channel.onClose(() => window.removeEventListener('pointermove', onMove))
```

> Lossy sends work in both directions. Leave out `lossy` for messages you want delivered in order, such as the final position of a drag. Use `ack: true` only on reliable sends.


## `Broadcast`

Use `Broadcast` to publish messages to everyone subscribed to a key on the server:

```ts
// Environment: server

import { Broadcast } from 'telefunc'

const unsubscribe = Broadcast.subscribe('room:lobby', (message, info) => {
  console.log(message, info.seq)
})
await unsubscribe.opened

await Broadcast.publish('room:lobby', { text: 'Hello!' })
unsubscribe()
```

The listener receives `{ key, seq, timestamp }` as its second argument. The publish resolves to the same fields. Use `publishBinary()` and `subscribeBinary()` for bytes.

> Await the unsubscribe function's `opened` promise before relying on delivery. On the server, capture values from `getContext()` before subscribing and use them inside the callback.

### Delivery

Broadcast delivers to subscribers on the same server by default. To publish across servers, see <Link href="/stream/scale#broadcast" />.

The receipt's `seq` orders publishes for a key, including text and binary. Use it to spot gaps. A Redis failover can rewind the sequence.

> With Redis, messages published during a subscriber's Redis disconnection are missed. See <Link href="/broadcast-config">`onDeliveryLost`</Link> to refresh state, <Link href="/redis#errors" /> for Redis publish errors, and <Link href="/stream/cloudflare#delivery-guarantees" /> for Cloudflare delivery.


## `new BroadcastChannel()`

`new BroadcastChannel({ key })` lets you broadcast from and to the client-side (whereas `Broadcast` is server-side only).

> It creates a `Channel` to the one client that received it, and bridges that client onto a `Broadcast` key.
>
> Return it from a telefunction and the receiving client can `publish()` / `subscribe()` on the key — the server fans each message out to the members subscribed to the key, client-side and server-side. For a client that falls behind, see `lossy` and <Link href="#errors" /> below.


<Warning>

Returning a `BroadcastChannel` gives the client access to its key. For private broadcasts, derive the key from authorized server-side context, such as the user ID from <Link href="/getContext">`getContext()`</Link>. To use a public key with private data, publish a refresh signal and fetch the data through an authorized telefunction. See <Link href="/stream#authorization" />.
</Warning>

### Chat example

```ts
// Chat.telefunc.ts
// Environment: server

import { Broadcast, BroadcastChannel } from 'telefunc'

type ChatMessage = { user: string; text: string }

// A public chat: any page may join any room, under any name
export async function onJoinChat(room: string, username: string) {
  const key = `chat:${room}`
  const chat = new BroadcastChannel<ChatMessage>({ key })

  chat.onOpen(() => {
    chat.publish({ user: 'system', text: `${username} joined` })
  })

  chat.onClose(() => {
    // The channel is closed: publish from the server
    Broadcast.publish(key, { user: 'system', text: `${username} left` })
  })

  return chat
}
```

> Unlike channels (`new Channel()`), no `.client` is needed: broadcast is symmetric — the same instance has the same message type on both ends (no directional flip).

```ts
// Chat.tsx
// Environment: client

import { onJoinChat } from './Chat.telefunc'

const chat = await onJoinChat('lobby', 'Alice')

// Receive messages published to the key, including this instance's own publishes
const unsubscribe = chat.subscribe((msg, info) => {
  console.log(`#${info.seq} ${msg.user}: ${msg.text}`)
})
await unsubscribe.opened

// Publish to every subscriber of the key
chat.publish({ user: 'Alice', text: 'Hello!' })
```

> A telefunction called after `subscribe()` runs once the subscription is in effect. For a plain HTTP request such as fetching a snapshot, await `unsubscribe.opened` first.

To receive messages in a loop, use `for await (const { type, data, info } of chat.messages({ signal }))`. Breaking out of the loop leaves the broadcast open. The loop holds up to 2 MiB of pending messages and frees them as you read.

### Notifications

A per-user key: the server returns a `BroadcastChannel` keyed to the signed-in user, and the client listens:

```ts
// Notifications.telefunc.ts
// Environment: server

import { Abort, BroadcastChannel, getContext } from 'telefunc'

export async function onListenNotifications() {
  const context = getContext()
  if (!context.userId) throw Abort()
  const broadcast = new BroadcastChannel({ key: `notifications:${context.userId}` })
  // Send a toast to *all* clients matching the user id, i.e. on all the tabs of
  // all the user's devices.
  setTimeout(() => broadcast.publish('hello'), 1000)
  setTimeout(() => broadcast.publish('world'), 2000)
  return broadcast
}
```

```ts
// Notifications.tsx
// Environment: client

import { onListenNotifications } from './Notifications.telefunc'

const broadcast = await onListenNotifications()
broadcast.subscribe((n) => showToast(n))
```

### Lossy broadcast

A client that falls behind skips superseded publishes with `lossy: true`:

```ts
// Prices.ts
// Environment: server

import { Broadcast } from 'telefunc'

stockFeed.on('price', ({ symbol, price }) => Broadcast.publish(`price:${symbol}`, price, { lossy: true }))
```

Give each value its own key and subscribe to that key with a `BroadcastChannel`. Use `lossy` with `publish()` or `publishBinary()` on either Broadcast API.

### `BroadcastChannel` methods

| Method | Description |
|---|---|
| `publish(data, { lossy? }?)` | Publish to every subscriber of the key. Returns a receipt. |
| `subscribe(cb)` | Receive `(data, info)`. Returns an unsubscribe function, whose `opened` promise resolves once the subscription is in effect, or once you remove it while the channel is open. |
| `publishBinary(data, { lossy? }?)` | Publish raw binary to every subscriber. Returns a receipt. |
| `subscribeBinary(cb)` | Receive `(data, info)` for binary messages. Returns an unsubscribe function whose `opened` promise follows the same rules. |
| `messages({ signal })` | Receive text and binary messages, each with its `info`, in a `for await` loop. |
| `onOpen(cb)` | Called when the channel opens. |
| `onClose(cb)` | Called when the channel closes. |
| `onDisconnect(cb)` / `onReconnect(cb)` | Called when the other side becomes unreachable / is back. See <Link href="#reconnection" />. |
| `isConnected` | `true` from `onOpen` until `onClose`, except while the other side is unreachable. |
| `opened` | Promise that resolves when the channel opens. |
| `closed` | Promise that resolves when the channel has closed: with `null`, or with the error it ended with. |
| `close()` | Close gracefully. Resolves with `null` once closed, or with the error it ended with. |
| `abort(abortValue?)` | Terminate immediately. |

> The instance is bound to its `key`, so `publish(data)` / `subscribe(cb)` take no key. The static <Link href="#broadcast"><code>Broadcast.publish(key, data)</code></Link> / `Broadcast.subscribe(key, cb)` have no `onOpen` / `onClose` / `close` / `abort` since there's no instance to manage.

> Pass `{ signal }` after a subscription or event callback to remove it on abort. Static `Broadcast.subscribe()` and `Broadcast.subscribeBinary()` accept it too.


## `new BroadcastChannel()` VS `new Channel()`

### Fundamentally

The difference is what a message is addressed to: a channel message is addressed to *someone*, a broadcast message is addressed to *a topic* (the `key`).

A channel is a conversation, like a phone call: two fixed ends (the server and the one client that received the channel), private to them, ending when either side hangs up.

A broadcast is an announcement, like a radio frequency: whoever tunes in to the `key` hears what is published to it, members come and go, and the `key` belongs to no one.

Only the two ends of a channel can use it, while anything that knows a broadcast's `key` can join it. A channel ends when either side closes it, while a broadcast outlives any single member.

### Technically

`new BroadcastChannel()` is essentially `new Channel()` combined with the static `Broadcast.publish()` / `Broadcast.subscribe()`: the server holds a private channel to the one client that received it, then bridges that client into the keyed broadcast group.

### Comparison

| | `new Channel()` | `new BroadcastChannel()` |
|---|---|---|
| Topology | One server ↔ one client | All members sharing a `key` (server and client) |
| Methods | `send()` / `listen()` | `publish()` / `subscribe()` |
| Delivery | The other end | Every subscriber of the `key`, including the publisher |
| Message type | Asymmetric:<ul><li>Two different types: `Channel<ClientMessageType, ServerMessageType>`</li><li>The server uses the `new Channel()` instance, and returns `channel.client` to the client</li></ul> | Symmetric:<ul><li>Same type for every member: `BroadcastChannel<MessageType>`</li><li>The server uses and returns the same `BroadcastChannel` instance</li></ul> |
| Message return | The other end's reply (if `{ ack: true }`) | A receipt: `{ key, seq, timestamp }` |
| Skip to the newest | Per send, in either direction: `send(data, { lossy: true })` | Per publish, from any member: `publish(data, { lossy: true })` |
| `close()` | Closes the channel for both ends | Detaches this member; the group lives on |
| Multi-server | <Link href="/stream/scale#sticky-sessions">Sticky sessions</Link> | <Link href="/stream/scale#sticky-sessions">Sticky sessions</Link> and a <Link href="/stream/scale#broadcast">cross-instance backend</Link> |


## Errors

Use `await` inside `try` to handle errors from a send or publish.

| Error | When | Channel state | Recovery |
|---|---|---|---|
| `Abort` | Either side called `abort(value)`, or a callback threw `Abort` | Closed | Inspect `err.abortValue` |
| `NetworkError` (`isChannel: true`) | Connection lost beyond `reconnectTimeout`, replay evicted while offline, or, on the server, the user left the page | Closed | Auto-closed — recreate if needed |
| `ChannelClosedError` | `send()` on a closed channel | Closed | Recreate the channel |
| `ChannelOverflowError` | A `send()` hit the server's memory limit | **Open** | `await` your sends (only that call rejects; `{ ack: true }` may have run already) |
| `ChannelOverflowError` | Client messages outran the server's memory limit | Closed | Recreate the channel; `await` sends and finish `listen()` callbacks sooner |
| `ChannelOverflowError` | A broadcast subscriber fell behind | Closed | Rejoin, read faster, or use `lossy: true` |
| `BackendError` (`publish()`) | With <Link href="/redis">`@telefunc/redis`</Link>, Redis couldn't run the publish | Open | See <Link href="/redis#errors">Redis errors</Link> |

> A graceful `close()` isn't an error (`onClose(err)` receives `null`).

## Reconnection

If the connection drops, Telefunc reconnects automatically and resends the reliable messages it still holds. Use `onDisconnect()`, `onReconnect()`, and `isConnected` to show connection status.

> If the client can't get back within <Link href="/channel-config">`reconnectTimeout`</Link>, the channel closes with `NetworkError`. Call its telefunction again to open a new one.
