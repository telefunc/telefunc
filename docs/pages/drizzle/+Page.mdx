Live queries for [Drizzle ORM](https://orm.drizzle.team) — write an ordinary Drizzle query, end it with `.live()`, and Telefunc keeps the result current. The dependencies come from the SQL you already wrote: nothing to subscribe to, no invalidation keys to maintain.

<PoweredByTelefuncStream pkg="drizzle" />

## Quickstart

```bash
npm install @telefunc/drizzle
```

Wrap your Drizzle `db` once and export it:

```ts
// db.ts
import { reactiveDrizzle } from '@telefunc/drizzle'
import { db } from './drizzle'

export const rdb = reactiveDrizzle(db)
```

End a read with `.live()`. Writes stay ordinary Drizzle:

```ts
// Todos.telefunc.ts
// Environment: server

import { eq } from 'drizzle-orm'
import { rdb } from './db'
import { todos } from './schema'

export async function onGetTodos(userId: number) {
  return rdb.select().from(todos).where(eq(todos.userId, userId)).live()
}

export async function onAddTodo(text: string) {
  await rdb.insert(todos).values({ text })
}
```

On the client you get a `Live<Todo[]>` — read `.data`. Because `onAddTodo` ran through the reactive `db`, Telefunc knows it touched rows this query reads, and tells the clients reading it to refetch:

```ts
// Environment: client
const todos = await onGetTodos(userId)
todos.data // Todo[]
```

That is the whole loop. Use <Link href="/tanstack-query">`@telefunc/tanstack-query`</Link> to do the refetching for you.

Works on PostgreSQL (including PGlite) and SQLite. `reactiveDrizzle()` refuses a MySQL database rather than accepting one whose writes it has no verified way to capture.


## Everything else is ordinary Drizzle

`await` the same chain without `.live()` for plain rows; `execute`, `prepare` and the dialect runners behave as before:

```ts
const rows = await rdb.select().from(todos)          // Todo[]       — plain read
const live = await rdb.select().from(todos).live()   // Live<Todo[]> — live read
```

> Forgetting `.live()` is a *compile* error at the boundary, not a silent bug: `Todo[]` is not a `Live<Todo[]>`.

> `reactiveDrizzle(db)` binds to nothing request-scoped — call it at module level, or inside a telefunction, before or after an `await`. There are no usage rules to remember.

Compose live values with `Live.derived()`. Reading a dependency's `.data` inside the callback registers it, and the derived value goes stale whenever a dependency does:

```ts
import { Live } from 'telefunc'

const openCount = Live.derived(() => todos.data.filter((t) => !t.done).length)
```


## How it works & limits

You can use Telefunc without reading this section. It is here for when you want to know why a query refetched, or are deploying more than one server.

### Precision

Live queries are **precise where that can be proven, and deliberately coarse — never wrong — everywhere else.** A coarse invalidation refetches more than strictly necessary; it never delivers a stale or fabricated row. Coarse is also temporary: after a raw statement, a migration, or a gap detected in the change stream, the affected queries refetch, rebuild their tracking, and go back to being precise.

Capturing a write precisely means recovering the rows it changed — and, for anything that retracts a row, a usable primary key. Read the table top to bottom: a write is precise only if no coarse row below it also applies.

| Your write | Behaviour |
| --- | --- |
| With your own `.returning()` — full, or a projection like `.returning({ id })` | **Precise** on any PostgreSQL or SQLite connection, **pooled included**: the rows come from the very session that ran the statement. For a projection Telefunc widens the `RETURNING` internally and hands you back exactly the columns you asked for |
| On **PGlite**, with no `.returning()` | **Precise** — its plain driver result can be reproduced faithfully |
| Anything else with no `.returning()` | **Coarse** — the plain driver result can't be reproduced faithfully, so the rows aren't captured |
| A **prepared** write with a *partial* `.returning()`, or with none | **Coarse on every driver, PGlite included** — `prepare()` freezes the statement, so Telefunc can neither add a `RETURNING` to it nor widen a projection into one. With a *full* `.returning()` a prepared write is precise on every execution: one decision covers them all |
| `UPSERT` / `ON CONFLICT`; an update or delete on a table with **no primary key**; a `.returning()` selecting a computed expression like ``sql`id + 1` `` | **Coarse even with `.returning()`** — a returned row doesn't say whether it was inserted or updated, a retraction has nothing to key on, and a value the database computed can't be recovered from the row. An **insert** into a key-less table is still precise: it carries its whole row and retracts nothing |

On **PostgreSQL 18 or newer**, an update or delete also returns the row's old image beside the new one, so a live query can tell a change it does not care about from one that moves a row in or out of its result — and primary-key-changing updates stay precise instead of coarsening. Telefunc **probes** for this once per database rather than trusting a version number, using a transaction it always rolls back: `telefunc_old_new_probe` in your query log is that probe, and it leaves nothing behind. If the role may not create temporary tables, Telefunc reads `server_version_num` instead and confirms the capability on the first write that relies on it.

Two over-fires are worth knowing about. Where you did not supply a full `RETURNING` yourself, Telefunc adds one — and a role that may write a table but not `SELECT` from it refuses that clause, so Telefunc re-runs your statement exactly as you wrote it and invalidates coarsely instead. **Your write never fails for a clause you did not ask for.** And a live *read* over a **pooled** connection stays coarse: a read's meaning depends on the session it runs in, and a pool can hand the next one a different role or `search_path`.

### Raw SQL

A raw statement's tables are unknowable without parsing it, so running one on the reactive db invalidates **every** table that db has a live query on — raw *reads* included:

```ts
await rdb.execute(sql`update todos set done = true`) // invalidates everything this db watches
await db.execute(sql`select count(*) from audit_log`) // base db — invalidates nothing
```

Run raw reads on your base `db` to avoid the noise.

### More than one server

The built-in default fans writes out **within one process** — enough for development and a single server. More than one needs a shared transport, or a write on one server will not reach a live query on another:

```ts
const rdb = reactiveDrizzle(db, {
  changeTransport: myRedisChangeTransport,
  changeNamespace: 'orders-db', // which logical database this is
})
```

`changeNamespace` is **required** alongside a transport: it must be identical on every server talking to the same database, and different for every other database sharing the broker. Without it two databases would exchange row changes. This transport is dedicated to live queries and independent of your app's `config.broadcast.transport`.

A transport carries an opaque string — Telefunc encodes the change itself, so you never have to make `BigInt`, `Date` or byte columns survive your serializer:

```ts
type ChangeTransport = {
  publish(topic: string, payload: string): void | Promise<void>
  subscribe(topic: string, onPayload: (payload: string) => void): Promise<{ unsubscribe(): void | Promise<void> }>
}
```

Two rules make it correct:

- **Resolve `subscribe()` once the subscription really exists** — after Redis acknowledges `SUBSCRIBE`, not when the command is sent. A live read waits on that promise, so resolving early re-opens the gap it closes. Likewise resolve `unsubscribe()` only once the listener is detached.
- **Deliver each payload at least once, byte for byte.** You do not have to deduplicate or preserve order: every message carries its publisher and a sequence number, so Telefunc drops repeats itself and falls back to a coarse refetch if it sees a gap or a reordering.

A db keeps the transport it first used, so passing a *different* one while live queries are running is an error rather than a silent swap. Once the db is quiescent — no live query holding a subscription — passing a different transport rotates it, which is what lets you replace a client or reset between tests.

### Delivery

Invalidation is best-effort pub/sub. A live read is not admitted until the transport confirms its subscription, so a write can't be missed in the gap between the two, and a detectable loss — a repeat, a gap, a reordering — falls back to a coarse refetch rather than applying a delta out of order.

A server that starts listening to a publisher already running takes the first message it sees at face value rather than assuming the worst. If an earlier one then arrives late, that is the proof the assumption was wrong and it triggers one corrective refetch; until then the query is briefly **missing a change rather than merely out of date**. Assuming the worst on every reconnect would instead drop those queries to coarse permanently, which costs more, far more often.

One case stays undetectable: if the *last* message from a publisher is dropped, no later message exists to reveal the gap, and that query's invalidation waits for the next write touching the table. Bounded staleness, never a fabricated row.

### Abandoned live reads

A `.live()` reserves state and hands it to the client connection when the handle is serialized. A handle that is **never** returned to the client — your telefunction builds one and then throws, or returns something else — has nothing to hand it to, so that state waits for garbage collection instead, which the JavaScript spec does not bound. What it holds is not negligible: the whole graph for that query, including hydrated row state. Failure paths that never produce a handle at all release immediately.
