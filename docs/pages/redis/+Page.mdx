Use Redis to share <Link href="/channel#broadcast">broadcasts</Link> and <Link href="/room">rooms</Link> across your Telefunc servers: a `publish()` on one server reaches every `subscribe()` on every other server.

> You only need this if you scale horizontally — see <Link href="/stream/scale" />.

## Install

```bash
npm install @telefunc/redis ioredis
```

Point every Telefunc server at the same Redis 5 or later:

```ts
// Environment: server

import IORedis from 'ioredis'
import { installRedis } from '@telefunc/redis'

const redis = new IORedis('redis://localhost:6379')
installRedis(redis)
```

That single call installs the Redis backend for both Broadcast and Room. Call `installRedis()` before your server first uses Broadcast or Room, for example in a module your server entry imports first.

> Room keeps its state in Redis: use `maxmemory-policy noeviction`, as any other policy can close a room.

### Sharing an existing client

Pass an existing [`ioredis`](https://github.com/redis/ioredis) Redis or Cluster instance to reuse its options, such as TLS or authentication.

```ts
// Environment: server

import IORedis from 'ioredis'
import { installRedis } from '@telefunc/redis'

const redis = new IORedis(process.env.REDIS_URL, { tls: {} })
installRedis(redis)
```

You can keep using the client you pass to Telefunc. To rotate credentials, call `installRedis()` again with a client that uses the new credentials for the same Redis.

To prefix Telefunc's Redis keys, pass `installRedis(redis, { prefix })` (default: `tf:`). Keep the keys under that prefix to Telefunc.

### A Redis user of its own

To give Telefunc a Redis user that may do only what it needs, create it on Redis 7 or later with this [ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/) rule, with your prefix in place of `tf:`:

```bash
redis-cli ACL SETUSER telefunc on '>your-password' '~tf:*' resetchannels '&tf:*' +evalsha +eval +get +set +del +unlink +exists +type +incr +pexpireat +time +hget +hmget +hset +hdel +hexists +hlen +hkeys +hscan +sadd +srem +scard +smembers +sscan +zadd +zrem +zrangebylex +zrangebyscore +publish +subscribe +unsubscribe +ping +info +client\|setname +cluster\|slots +cluster\|info +asking
```

Then connect as that user, with the same prefix:

```ts
// Environment: server

import IORedis from 'ioredis'
import { installRedis } from '@telefunc/redis'

const redis = new IORedis('redis://telefunc:your-password@localhost:6379')
installRedis(redis, { prefix: 'tf:' })
```

## Errors

A `publish()` or a Room call that Redis can't run rejects with `BackendError`:

```ts
// Environment: server

import { Broadcast, BackendError } from 'telefunc'

try {
  await Broadcast.publish('chat', message)
} catch (err) {
  if (!(err instanceof BackendError)) throw err
  console.error(err.message) // What failed and what to do, with Redis's error code, such as `NOPERM`
  err.code // 'unreachable' | 'unavailable' | 'denied' | 'failed'
  err.outcome // 'not-run' | 'may-have-run'
}
```

| `code` | When | What to do |
|---|---|---|
| `'unreachable'` | The connection to Redis failed or closed, or Redis didn't answer within 15 s (or the `commandTimeout` of the client you pass) | Call again once Redis is reachable |
| `'unavailable'` | Redis can't serve it now, and a later call may succeed: it is loading its data, busy, out of memory, a replica, or its replicas are behind | Call again later. If it lasts, see the message: out of memory, Redis needs a higher `maxmemory`; for a replica, give `installRedis()` a client of the primary |
| `'denied'` | Redis refuses it until you change its ACL, the password, or a command its operator disabled | Change that, then call again |
| `'failed'` | Redis failed it otherwise | See the message |

If `err.outcome` is `'not-run'`, the call changed nothing: you can call it again once you've corrected the cause.

It is `'may-have-run'` when the call may have taken effect, for example when the connection dropped before Redis answered:

| Call | After `'may-have-run'` |
|---|---|
| `Broadcast.publish()`, `Room.publish()`, `Room.send()`, a participant's `publish()` and `send()` | Publishing again can deliver the message twice |
| `Room.create()` | Call `Room.get()`: a second `Room.create()` rejects with `ROOM_EXISTS` if the first took effect. Or use `Room.getOrCreate()` |
| `Room.close()`, `Room.setMeta()`, `Room.updateMeta()`, a participant's `setMeta()`, `updateMeta()` and `leave()` | Call it again: two calls end as one does |
| `Room.removeParticipant()` | Call it again. With `{ identity }`, two calls end as one does. With `{ id }`, a second call that rejects with `PARTICIPANT_NOT_FOUND` or `ROOM_NOT_FOUND` means the participant is no longer in the room |
| `Room.join()`, `room.join()` | Join again: Telefunc removes the participant of the failed join |
| `Room.get()`, `Room.list()`, `Room.getParticipants()` | Call it again: you can retry a read regardless of `outcome` |

## Subscriptions

While Redis is unreachable, a new subscription's `opened` waits until Redis is back. A subscription already in effect stays, and its callback receives what is published once Redis is back (see <Link href="/channel#delivery">Delivery</Link> for what it missed).

A subscription fails when Redis refuses it, for example when its ACL denies a channel the subscription needs. Restore the access, then subscribe again; your server's log and <Link href="/onBug">`onBug()`</Link> say what Redis refused.

> A <Link href="/channel#new-broadcastchannel">`BroadcastChannel`</Link> closes: on the client, the callback you pass to `onClose()` gets a `ChannelClosedError`. Call its telefunction again and subscribe to the broadcast it returns.

> A `Broadcast.subscribe()` is removed: if its `opened` hadn't resolved, it rejects with a `BackendError`. Call `Broadcast.subscribe()` again.

Await `opened` before you depend on that listener receiving a publish:

```ts
// Chat.telefunc.ts
// Environment: server

import { Broadcast } from 'telefunc'

const subscription = Broadcast.subscribe(key, listener)
await subscription.opened
```

## Channels

`Channel` is per-instance. Reconnects must land on the instance holding the channel's state, so multi-instance deployments need sticky sessions at the load balancer. See <Link href="/stream/scale" />.

## Limitations

- A message is 28 MiB at most: a `publish()` or `publishBinary()` over that rejects with `ChannelOverflowError`. At its default [output buffer limits](https://redis.io/docs/latest/develop/reference/clients/#output-buffer-limits), Redis closes the connection that receives a larger message. For a larger payload, publish a reference to it, such as a URL.
- Redis replicates asynchronously, so a failover can lose a write the old primary acknowledged, such as a `Room.updateMeta()` that resolved just before it. The rooms on every server then catch up to what the new primary holds.
- Telefunc follows a failover through Redis Sentinel or Redis Cluster. A `FAILOVER` of a standalone Redis without Sentinel gives no new primary to follow: use Sentinel or Cluster for automatic failover.
