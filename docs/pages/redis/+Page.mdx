Redis-backed <Link href="/channel#broadcast">broadcast</Link> fan-out across server instances — a `publish()` on any instance reaches every `subscribe()` on every other instance, <Link href="/channel#delivery">at most once</Link>. <Link href="/room">Rooms</Link> work across instances too.

> You only need this if you scale horizontally — see <Link href="/stream/scale" />.

## Install

```bash
npm install @telefunc/redis ioredis
```

Requires Redis 5 or later, and Redis 7 or later for a <Link href="#a-redis-user-of-its-own">Redis user whose ACL doesn't allow every command</Link>.

```ts
// Environment: server

import IORedis from 'ioredis'
import { installRedis } from '@telefunc/redis'

const redis = new IORedis('redis://localhost:6379')
installRedis(redis)
```

That single call installs the Redis backend for both Broadcast and Room. Room state and events are then shared across server instances. Call `installRedis()` before your server first uses Broadcast or Room, for example in a module your server entry imports first.

### Sharing an existing client

Pass an existing [`ioredis`](https://github.com/redis/ioredis) Redis or Cluster instance to reuse its options, such as TLS or authentication.

```ts
// Environment: server

import IORedis from 'ioredis'
import { installRedis } from '@telefunc/redis'

const redis = new IORedis(process.env.REDIS_URL, { tls: {} })
installRedis(redis)
```

Telefunc duplicates the supplied client as needed without disconnecting it, so you can continue to use it alongside Telefunc. To rotate credentials, call `installRedis()` again with a client of the same Redis that has the new ones: Telefunc moves its connections to it.

To prefix Telefunc's Redis keys, pass `installRedis(redis, { prefix })`.

### A Redis user of its own

To give Telefunc a Redis user that may do only what it needs, create it with this [ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/) rule, with your prefix in place of `tf:`:

```
ACL SETUSER telefunc on >your-password ~tf:* resetchannels &tf:* +evalsha +eval +get +set +del +unlink +exists +type +incr +pexpireat +time +hget +hmget +hset +hdel +hexists +hlen +hkeys +hscan +sadd +srem +scard +smembers +sscan +zadd +zrem +zrangebylex +zrangebyscore +publish +subscribe +unsubscribe +ping +info +client|setname +client|setinfo
```

Such a user needs Redis 7 or later: there, a `publish()` or a room change that Redis refuses leaves nothing behind.

Room keeps its state in Redis: use `maxmemory-policy noeviction`, as any other policy can close a room.

Telefunc's Redis backend takes a message of 28 MiB at most: a `publish()` or `publishBinary()` over that rejects with `ChannelOverflowError`. Telefunc chose this ceiling because, at its default [output buffer limits](https://redis.io/docs/latest/develop/reference/clients/#output-buffer-limits), Redis closes the connection of a server it sends a larger message (measured on Redis 7.4). Raising those limits doesn't lift the ceiling.

## Errors

A `publish()` or a Room call that Redis can't run rejects with `BackendError`:

```ts
// Environment: server

import { Broadcast, BackendError } from 'telefunc'

try {
  await Broadcast.publish('chat', message)
} catch (err) {
  if (!(err instanceof BackendError)) throw err
  console.error(err.message) // What failed and what to do, with Redis's error code, such as `NOPERM`
  err.code // 'unreachable' | 'unavailable' | 'denied' | 'failed'
  err.outcome // 'not-run' | 'may-have-run'
}
```

| `code` | When | What to do |
|---|---|---|
| `'unreachable'` | The connection to Redis failed or closed | Call again once Redis is reachable |
| `'unavailable'` | Redis can't serve it now, and a later call may succeed: it is loading its data, busy, out of memory, a replica, or its replicas are behind | Call again later. If it lasts, see the message: out of memory, Redis needs a higher `maxmemory`; for a replica, give `installRedis()` a client of the primary |
| `'denied'` | Redis refuses it until you change its ACL, the password, or a command its operator disabled | Change that, then call again |
| `'failed'` | Redis failed it otherwise | See the message |

`outcome` is `'not-run'` when the call changed nothing: Redis refused it before running it, Telefunc never sent it because the connection was down, or a key under Telefunc's prefix holds what Telefunc didn't write, which Telefunc checks before it writes (`code` is then `'failed'`: keep the prefix to Telefunc). Calling again is safe.

It is `'may-have-run'` when the call may have taken effect, for example when the connection dropped before Redis answered:

| Call | After `'may-have-run'` |
|---|---|
| `Broadcast.publish()`, `Room.publish()`, `Room.send()`, a participant's `publish()` and `send()` | Publishing again can deliver the message twice |
| `Room.create()` | Call `Room.get()`: a second `Room.create()` rejects with `Room already exists` if the first took effect. Or use `Room.getOrCreate()` |
| `Room.close()`, `Room.setMeta()`, `Room.updateMeta()`, a participant's `setMeta()`, `updateMeta()` and `leave()` | Call it again: two calls end as one does |
| `Room.removeParticipant()` | Call it again. With `{ identity }`, two calls end as one does. With `{ id }`, a second call that rejects with a `RoomError` (`err instanceof RoomError`) means the participant is no longer in the room: the first call took effect, or the room closed |
| `Room.join()`, `room.join()` | Join again: Telefunc removes the participant of the failed join, at once or at its next heartbeat |
| `Room.get()`, `Room.list()`, `Room.getParticipants()` | Call it again: a read is safe to call again whatever its `outcome` says. It says `'may-have-run'` when it had cleaned up after a participant or a room that had lapsed |

While Redis is unreachable, a new subscription's `ready` waits until Redis is back. A subscription already in effect stays, and its callback receives what is published once Redis is back (see <Link href="/channel#delivery">Delivery</Link> for what it missed).

A subscription fails when Redis refuses it: its ACL denies a command, key or channel the subscription needs, or the server is a replica (`READONLY`). That can happen when it starts, and also when Telefunc subscribes again after the connection to Redis dropped. The server reports the refusal through <Link href="/onBug">`onBug()`</Link> and its log. Telefunc isn't told when Redis allows it again, so subscribe again once you have restored the access.

> A <Link href="/channel#new-broadcastchannel">`BroadcastChannel`</Link> closes. On the server, its error is a `BackendError`, whose message says what Redis refused, with Redis's error code, such as `NOPERM`. On the client, the callback you pass to `onClose()` gets a `ChannelClosedError`, and `ready` rejects with one if it hadn't resolved. Call its telefunction again and subscribe to the broadcast it returns.

> A `Broadcast.subscribe()` is removed, and its callback receives nothing more. If its `ready` hadn't resolved, it rejects with a `BackendError`, whose message says what Redis refused. Call `Broadcast.subscribe()` again.

> A `publish()` the server makes to a key while its subscription to that key's text messages is new waits for it, and fails with the subscription's refusal where Redis refuses it: the server's own subscribers would miss it. A failed `Broadcast.subscribeBinary()` does the same to `publishBinary()`. A publish made once the failed subscription is over goes out, and so do publishes of the key's other kind and to other keys.

## Channels

`Channel` is per-instance. Reconnects must land on the instance holding the channel's state, so multi-instance deployments need sticky sessions at the load balancer. See <Link href="/stream/scale" />.
