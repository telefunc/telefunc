## Setup

```ts
// worker.ts
// Environment: server

import { Telefunc } from 'telefunc/cloudflare'

const telefunc = new Telefunc()

export const TelefuncDurableObject = telefunc.TelefuncDurableObject

export default {
  async fetch(request: Request, env: Env) {
    const response = await telefunc.serve({ request, env })
    if (response) return response

    return new Response('Not found', { status: 404 })
  },
}
```

> Fundamentally, channels are stateful: the server holds live state for each open channel. Cloudflare Workers, however, are stateless and ephemeral — any request can be served by any worker, and nothing is remembered between requests. The state therefore needs to live somewhere else — Durable Objects are Cloudflare's primitive for exactly that: each channel lives on a Durable Object, which holds the connection and its state.
>
> The Durable Object binding is required whenever you use `telefunc/cloudflare`. If your app doesn't use `Channel`, `Broadcast`, or `Room`, you can skip this binding and use <Link href="/serve"><code>serve()</code></Link> instead.
>
> See <Link href="#architecture" /> for implementation details.

## Architecture

Telefunc uses [Durable Objects](https://developers.cloudflare.com/durable-objects/) for <Link href="/channel">channel</Link> state and <Link href="/channel#broadcast">broadcast</Link> fan-out. Channel state is in-memory JavaScript (closures, callbacks, local variables), so it must live on the same Durable Object that holds the WebSocket connection.

### Regions

Telefunc maps each request to one of six geographic regions using Cloudflare's colocation data:

| Region | Code |
|---|---|
| West North America | `wnam` |
| East North America | `enam` |
| West Europe | `weur` |
| East Europe | `eeur` |
| Asia Pacific | `apac` |
| Oceania | `oc` |

Each region runs its own Durable Objects so that channel state stays close to users.

### Session affinity

Every telefunction call and channel message from a client must reach the **same Durable Object** — otherwise that client's channel state would be unavailable.

The client sends a session token with every request, as the `session` query parameter. Telefunc routes all requests with the same token to the same Durable Object, in the region nearest to the client.

That Durable Object names its region in its responses' `x-telefunc-home` header, and the client then sends it as the `home` query parameter, so its requests reach the same Durable Object from any region.

<Warning>

**CDN / reverse proxy** — make sure the `session` and `home` query parameters aren't stripped from requests, nor the `x-telefunc-home` header from responses (a cross-origin server exposes it with `Access-Control-Expose-Headers`). Without the token, each request would be routed to a random Durable Object and channel state would be lost.

</Warning>


### Rooms

<Link href="/room">Room</Link> calls such as `Room.create()`, `Room.announce()` and `Room.close()` work anywhere in your Worker, including cron triggers and queue consumers. A server-side listener (`subscribe()`, `onJoin()`, …) runs on the Durable Object of the client whose request installed it (see <Link href="#session-affinity" />), so install it inside a telefunction or a channel handler.

A room's state lives in one Durable Object, in the region of the client that created the room (or in the <Link href="#configuration">`locationFallback`</Link> region, for a room created from a cron trigger or a queue consumer). A participant in another region waits two round trips to that region for `room.join()`, and one to leave, change their participant metadata or send a message. A join, a leave and a metadata change also wait until the Durable Object of each other participant has them, which adds the round trip from the room's region to the furthest of them. `Room.join(id)` reads the room first. Messages and join and leave events travel from that region to each participant, so a participant in another region receives them about half a round trip later than one in the room's region.

The room's state is kept in its Durable Object's storage, so the room survives a deployment. A participant's connection doesn't: when the Durable Object holding the connection is evicted, the participant's `me.onLeave()` gets `cause.type: 'disconnected'`. Telefunc doesn't rejoin it for you: from `me.onLeave()`, call the telefunction that returned the room again (see <Link href="/room#create-and-join-a-room" />). The other participants see the old participant leave about two minutes later. That is the room's own timer, separate from the broadcast <Link href="#presence">presence</Link> TTL.

## Scaling

By default, Telefunc creates one Durable Object per region. Increase capacity with `scale`:

```ts
const telefunc = new Telefunc({ scale: 4 })
```

This creates 4 Durable Objects per region, and Telefunc distributes sessions across them.

### Per-region scale

```ts
const telefunc = new Telefunc({
  scale: { weur: 5, enam: 3, apac: 2 },
})
```

Only specified regions get Durable Objects. Requests from unspecified regions fall back to <Link href="#configuration">`locationFallback`</Link>.


## Distributed broadcast

<Link href="/channel#broadcast">Broadcasts</Link> fan out across all regions automatically.

`publish()` works anywhere in your Worker, including cron triggers and queue consumers. A server-side `subscribe()` runs on the Durable Object of the client whose request installed it, so subscribe inside a telefunction or a channel handler.

### How it works

<Advanced>

You can skip this section — it's Telefunc's internal fan-out, not anything you configure.

</Advanced>

```
Publisher (Durable Object)
  → Authority DO (one per key — assigns sequence numbers)
    → Coordinators (one per active region)
      → Durable Objects (deliver to local subscribers)
```

1. The publisher forwards the message to an **authority** Durable Object for the key.
2. The authority assigns a monotonic sequence number, reads the key's presence from its own storage, and forwards to each region with subscribers.
3. Each region's coordinator fans out to the Durable Objects in that region.
4. Each Durable Object delivers to its local subscribers.

### Ordering

<Link href="/channel#broadcast">Broadcast</Link> publishes for a given `key` go through a single authority, which assigns a <Link href="/channel#broadcast">monotonic `seq`</Link>. Every subscriber receives them in `seq` order. The publishes of one Durable Object's telefunctions and channel handlers get their `seq` in call order. Any others get it in the order they reach the authority.

### Presence

Each key's authority records which Durable Objects have subscribers, in its own storage:

| Setting | Value |
|---|---|
| TTL | 90 seconds |
| Refresh | every 30 seconds |

A Durable Object registers with the authority on its first subscription to a key and withdraws on its last unsubscribe. If a Durable Object is evicted (e.g. during a deployment), its record lapses after 90 seconds and fan-out skips it.


## Delivery guarantees

### Channel messages (`send` / `listen`)

| Guarantee | Details |
|---|---|
| Ordering | Messages are delivered in order. |
| Buffering | The server buffers messages while the client is disconnected: up to `config.channel.bufferLimit` for text (default: 512 KB) and up to `config.channel.bufferLimitBinary` for binary (default: 2 MB). Binary frames have a separate budget and can never evict text. |
| Replay | Both sides keep a replay buffer. On reconnect, missing messages are replayed and duplicates are ignored. |
| Acknowledgements | `send(data, { ack: true })` resolves when the other side processes the message. |
| Loss | If the disconnection lasts longer than `config.channel.reconnectTimeout`, or one side missed more messages than the replay buffer holds, the channel closes with <Link href="/channel#errors">`NetworkError`</Link>. |

### Broadcast messages (`publish` / `subscribe`)

| Guarantee | Details |
|---|---|
| Ordering | Every subscriber receives a key's publishes in `seq` order, which is call order for the publishes of one Durable Object's telefunctions and channel handlers. |
| Delivery | `publish()` resolves once the message has reached every Durable Object with subscribers. If a Durable Object can't take it, `publish()` rejects. That Durable Object's subscribers miss the message, while every other subscriber still gets it, so publishing it again delivers it twice to them. Delivery to clients then happens over the channel connection. |

> Once a broadcast message reaches a Durable Object, it has the same buffering and replay guarantees as regular channel messages.


## Configuration

```js
const telefunc = new Telefunc({
  bindingName: 'TelefuncDurableObject',  // DO binding name (default)
  instanceName: 'telefunc',              // Base name for DO instances (default)
  scale: 1,                              // DOs per region (default)
  locationFallback: 'weur',              // Fallback region (default)
  jurisdiction: 'eu',                    // Restrict DOs to a jurisdiction (optional, no default)
})
```

## Hibernation

> **[Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/#why-use-hibernation) while channels are open isn't supported.**
>
> Channel state is in-memory JavaScript. If the Durable Object hibernates, that state is gone. Telefunc keeps the Durable Object alive while channels are open.

The Durable Object can hibernate once all channels are closed, no clients remain connected, and both the reconnect and idle windows have expired.

```ts
import { config } from 'telefunc'

// Shorter windows = hibernate sooner, less disconnect tolerance
config.channel = {
  reconnectTimeout: 5_000,
  idleTimeout: 5_000,
  pingInterval: 2_000
}
```
