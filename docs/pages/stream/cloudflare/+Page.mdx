## Setup

```ts
// worker.ts
// Environment: server

import { Telefunc } from 'telefunc/cloudflare'

const telefunc = new Telefunc()

export const TelefuncDurableObject = telefunc.TelefuncDurableObject

export default {
  async fetch(request: Request, env: Env) {
    const response = await telefunc.serve({ request, env })
    if (response) return response

    return new Response('Not found', { status: 404 })
  },
}
```

> `nodejs_als` (or `nodejs_compat`, which includes it) is needed only when your server code subscribes to a broadcast. Without it, `Broadcast.subscribe()` throws an error that names the flag. So does `subscribe()` on a `BroadcastChannel` the client hasn't received yet, such as in the telefunction that returns it. Telefunctions, channels, and a `BroadcastChannel` the client subscribes to work without it.

> `enable_request_signal` is what lets <Link href="/onClose#context-signal">`context.signal` and `onClose()`</Link> see a client that disconnects before its telefunction answers.

> Fundamentally, channels are stateful: the server holds live state for each open channel. Cloudflare Workers, however, are stateless and ephemeral — any request can be served by any worker, and nothing is remembered between requests. The state therefore needs to live somewhere else — Durable Objects are Cloudflare's primitive for exactly that: each channel lives on a Durable Object, which holds the connection and its state.
>
> The Durable Object binding is required whenever you use `telefunc/cloudflare`. If your app doesn't use `Channel`, `Broadcast`, or `Room`, you can skip this binding and use <Link href="/serve"><code>serve()</code></Link> instead, keeping `enable_request_signal`.
>
> See <Link href="#architecture" /> for implementation details.

## Architecture

Telefunc uses [Durable Objects](https://developers.cloudflare.com/durable-objects/) for <Link href="/channel">channel</Link> state and <Link href="/channel#broadcast">broadcast</Link> fan-out. Channel state is in-memory JavaScript (closures, callbacks, local variables), so it must live on the same Durable Object that holds the WebSocket connection.

### Regions

Telefunc maps each request to one of six geographic regions using Cloudflare's colocation data:

| Region | Code |
|---|---|
| West North America | `wnam` |
| East North America | `enam` |
| West Europe | `weur` |
| East Europe | `eeur` |
| Asia Pacific | `apac` |
| Oceania | `oc` |

Each region runs its own Durable Objects so that channel state stays close to users.

### Session affinity

Every telefunction call and channel message from a client must reach the **same Durable Object** — otherwise that client's channel state would be unavailable.

The client sends a session token with every request, as the `session` query parameter. Telefunc routes all requests with the same token to the same Durable Object, in the region nearest to the client.

That Durable Object names its region in its responses' `x-telefunc-home` header, and the client then sends it as the `home` query parameter, so its requests reach the same Durable Object from any region.

<Warning>

**CDN / reverse proxy** — make sure the `session` and `home` query parameters aren't stripped from requests, nor the `x-telefunc-home` header from responses (a cross-origin server exposes it with `Access-Control-Expose-Headers`). Without the token, each request would be routed to a random Durable Object and channel state would be lost.

</Warning>


### Rooms

<Link href="/room">Room</Link> calls such as `Room.create()`, `Room.publish()` and `Room.close()` work anywhere in your Worker, including cron triggers and queue consumers. A server-side listener (`subscribe()`, `onJoin()`, …) runs on the Durable Object of the client whose request installed it (see <Link href="#session-affinity" />), so install it inside a telefunction or a channel handler.

A room's state lives in one Durable Object, in the room's region: the region of the client that created the room (or the <Link href="#configuration">`locationFallback`</Link> region, for a room created from a cron trigger or a queue consumer).

A participant outside the room's region waits one round trip to the room's region for `room.join()`: the join registers their inbox with it. The first time a client's Durable Object joins or subscribes to a room, it waits one more, for the grant that orders its subscriptions there. `Room.join(id)` reads the room first. Leaving, changing their participant metadata or sending a message takes that participant one round trip to the room's region.

A join, a leave, a metadata change and a private message also wait until they have reached the Durable Object of each participant concerned, which adds the round trip from the room's region to the furthest of those Durable Objects. Messages and join and leave events travel from the room's region to each participant, so a participant outside the room's region receives them about half a round trip later than one in it.

The room's state is kept in its Durable Object's storage, so the room survives a deployment. A participant's connection doesn't: when the Durable Object holding the connection is evicted, the participant's `me.onLeave()` gets `cause.type: 'disconnected'`. Telefunc doesn't rejoin it for you: from `me.onLeave()`, call the telefunction that returned the room again (see <Link href="/room#create-and-join-a-room" />). The other participants see the old participant leave about two minutes later. That is the room's own timer, separate from the broadcast <Link href="#presence">presence</Link> TTL.

## Scaling

By default, Telefunc creates one Durable Object per region. Increase capacity with `scale`:

```ts
const telefunc = new Telefunc({ scale: 4 })
```

This creates 4 Durable Objects per region, and Telefunc distributes sessions across them.

### Per-region scale

```ts
const telefunc = new Telefunc({
  scale: { weur: 5, enam: 3, apac: 2 },
})
```

Only specified regions get Durable Objects. Requests from unspecified regions fall back to <Link href="#configuration">`locationFallback`</Link>.


## Distributed broadcast

<Link href="/channel#broadcast">Broadcasts</Link> fan out across all regions automatically.

`publish()` works anywhere in your Worker, including cron triggers and queue consumers. A server-side `subscribe()` runs on the Durable Object of the client whose request installed it, so subscribe inside a telefunction or a channel handler. The subscription lives in that Durable Object's memory and ends when Cloudflare evicts the object, so it serves a client that stays connected.

Telefunc doesn't remove a server-side subscription when the client leaves. Remove it yourself: call the function `Broadcast.subscribe()` returns, or abort the `{ signal }` you passed to it (see <Link href="/channel#broadcast" />). If it forwards to a channel, remove it in that channel's `onClose()`. A page that only calls telefunctions doesn't tell the server that it left. A later call from the same client reaches the same Durable Object (see <Link href="#session-affinity" />), and another client's may not, so end the subscription from such a call or from a timer you set where you subscribed.

### How it works

<Advanced>

You can skip this section — it's Telefunc's internal fan-out, not anything you configure.

</Advanced>

```
Publisher (Durable Object)
  → Authority DO (one per key — assigns sequence numbers)
    → Coordinators (one per active region)
      → Durable Objects (deliver to local subscribers)
```

1. The publisher forwards the message to an **authority** Durable Object for the key.
2. The authority assigns a monotonic sequence number, reads the key's presence from its own storage, and forwards to each region with subscribers.
3. Each region's coordinator fans out to the Durable Objects in that region.
4. Each Durable Object delivers to its local subscribers.

### Ordering

<Link href="/channel#broadcast">Broadcast</Link> publishes for a given `key` go through a single authority, which assigns a <Link href="/channel#broadcast">monotonic `seq`</Link>. Every subscriber receives them in `seq` order. The publishes of one Durable Object's telefunctions and channel handlers get their `seq` in call order. Any others get it in the order they reach the authority.

### Presence

Each key's authority records which Durable Objects have subscribers, in its own storage:

| Setting | Value |
|---|---|
| TTL | 90 seconds |
| Refresh | every 30 seconds |

A Durable Object registers with the authority on its first subscription to a key and withdraws on its last unsubscribe. If a Durable Object is evicted (e.g. during a deployment), its record lapses after 90 seconds and fan-out skips it. A Durable Object that can't refresh for that long misses what is published until it registers again. The next refresh that reaches the authority learns that the record lapsed, and <Link href="/broadcast-config">`config.broadcast.onDeliveryLost`</Link> is called, once for that lapse.


## Delivery guarantees

### Channel messages (`send` / `listen`)

| Guarantee | Details |
|---|---|
| Ordering | Messages are delivered in order. |
| Buffering | The server holds messages while the client is disconnected, up to <Link href="/channel-config">`config.channel.maxMemory`</Link> (default on Cloudflare: 64 MiB, as a Durable Object's memory is limited to 128 MB). A message clears once the client confirms it. |
| Replay | On reconnect, missing messages are resent and duplicates are ignored. |
| Acknowledgements | `send(data, { ack: true })` resolves when the other side processes the message. |
| Loss | If the disconnection lasts longer than `config.channel.reconnectTimeout`, the channel closes with <Link href="/channel#errors">`NetworkError`</Link>. |

### Broadcast messages (`publish` / `subscribe`)

| Guarantee | Details |
|---|---|
| Ordering | Every subscriber receives a key's publishes in `seq` order, which is call order for the publishes of one Durable Object's telefunctions and channel handlers. |
| Delivery | `publish()` resolves once the message has reached every Durable Object with subscribers. If a Durable Object can't take it, `publish()` rejects. That Durable Object's subscribers miss the message, while every other subscriber still gets it, so publishing it again delivers it twice to them. Delivery to clients then happens over the channel connection. |
| Failed registration | A subscription takes effect once its Durable Object is <Link href="#presence">registered</Link> for the key. If that first registration fails, the subscription fails. Where Cloudflare marks the failure `.retryable` and not `.overloaded`, Telefunc first makes the registration again, up to 3 times in all and within 10 s of the first, as Cloudflare's [error handling](https://developers.cloudflare.com/durable-objects/best-practices/error-handling/) recommends; the server-side `ready` waits meanwhile, and the subscription fails with the last error. |

> Once a broadcast message reaches a Durable Object, it has the same buffering and replay guarantees as regular channel messages.

When a registration fails, at once or after its last attempt, the server reports the failure through <Link href="/onBug">`onBug()`</Link> and its log. Each `BroadcastChannel` that waited on it closes. On the client, the callback you pass to `onClose()` gets a `ChannelClosedError`, and `ready` rejects with one. Call its telefunction again and subscribe to the broadcast it returns. Each `Broadcast.subscribe()` that waited on it is removed, and its `ready` rejects with an error whose `cause` is the error the registration failed with: call `Broadcast.subscribe()` again. A failed registration doesn't fail publishes to the key. A refresh that fails ends no subscription (see <Link href="#presence">Presence</Link>).


## Configuration

```js
const telefunc = new Telefunc({
  bindingName: 'TelefuncDurableObject',  // DO binding name (default)
  instanceName: 'telefunc',              // Base name for DO instances (default)
  scale: 1,                              // DOs per region (default)
  locationFallback: 'weur',              // Fallback region (default)
  jurisdiction: 'eu',                    // Restrict DOs to a jurisdiction (optional, no default)
})
```

## Hibernation

> **[Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/#why-use-hibernation) while channels are open isn't supported.**
>
> Channel state is in-memory JavaScript. If the Durable Object hibernates, that state is gone. Telefunc keeps the Durable Object alive while channels are open.

When a page leaves, its channels close at once. When its connection drops instead, the server keeps its channels open for `reconnectTimeout`, so that the client gets them back if it reconnects in time. Lower it to close a gone client's channels sooner. For when a Durable Object with no open channel hibernates, see Cloudflare's [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/).

```ts
import { config } from 'telefunc'

// A dropped client gets 5 s to reconnect before its channels close; a silent one counts as dropped 4 s after its last ping
config.channel = {
  reconnectTimeout: 5_000,
  pingInterval: 2_000
}
```

## Workers Free

Cloudflare [lists](https://developers.cloudflare.com/workers/platform/limits/#cpu-time) 10 ms of CPU time per HTTP request on Workers Free. It states: "Each isolate has some built-in flexibility to allow for cases where your Worker infrequently runs over the configured limit. If your Worker starts hitting the limit consistently, its execution will be terminated according to the limit configured." The client then gets Error 1102.

> In one test of about 8 minutes of light traffic on Workers Free, 16 of 305 invocations ran past 10 ms of CPU and none was stopped. The highest was 55 ms, rendering a page with Vike, and a request to `/_telefunc` reached 34 ms.
>
> Sustained use on Workers Free wasn't measured, so this doesn't show that an app stays within the limit.
